## Highlight

> Instruments 15 新增了 RealityKit Trace 模板，为 visionOS 应用提供了专用的逐帧渲染分析、GPU 瓶颈检测和系统功耗评估工具，开发者可以直接在时间线中定位掉帧原因。

---

## 核心内容

空间计算应用有一个硬性约束：渲染必须在极短的时间内完成每一帧，否则用户会感知到卡顿。在传统平台上，偶尔掉几帧用户可能不会注意。但在 visionOS 上，渲染延迟直接对应视觉不连贯，轻则体验下降，重则引发不适。

问题在于，visionOS 的渲染管线比传统平台复杂得多。一帧画面要经过应用进程、渲染服务器和合成器三个组件协同工作。你在 Xcode 里写的 SwiftUI 或 RealityKit 代码只决定了「画什么」，但「怎么画」和「什么时候显示」由系统调度。这意味着性能瓶颈可能出现在任何一个环节，而且不同环节之间的交互会让问题更难定位。

RealityKit Trace 模板就是为解决这个问题而设计的。它不是通用的 Instruments 模板改了几个参数，而是为 RealityKit 渲染管线从头构建的一组专用工具。

模板包含三个核心 Instruments：

**RealityKit Frames** 负责逐帧追踪渲染时间。它把每一帧的 CPU 和 GPU 耗时拆开，用颜色标记：绿色表示远在截止时间内完成，橙色表示刚好赶上，红色表示超时导致掉帧。你只需要在时间线中找到红色密集的区域，就能快速定位出问题的时段。

**RealityKit Metrics** 负责瓶颈分析。它不只看「帧有没有按时完成」，还告诉你「为什么没完成」。它会分类统计各类渲染操作的耗时占比——实体更新、动画、物理模拟、材质加载等——每一项都标注了系统执行时间。结合这些指标，你能一眼看出是 3D 模型太复杂，还是每帧做了太多状态更新。

**系统功耗** 指标让你看到应用的能耗水平。visionOS 有一个关键特性：当系统检测到功耗过高时，会自动降低帧率来保护散热。你的应用可能在 Full Space 中跑满 90fps，但一旦功耗超标，系统会把帧率降到 60fps 甚至更低。功耗指标帮你在这个问题发生之前就发现它。

Session 用一个 Hello World 示例演示了完整的分析流程。这个示例展示卫星绕地球运行的沉浸式体验，因为使用了过于精细的 3D 模型导致交互卡顿。通过 RealityKit Trace，开发者发现卡顿的原因不是渲染本身慢，而是每帧都在做大量不必要的 offscreen 渲染——这些离屏绘制消耗了 GPU 资源却没有在屏幕上显示任何内容。

## 详细内容

### 渲染管线的三个组件（[00:30](https://developer.apple.com/videos/play/wwdc2023/10099/?time=30)）

理解 RealityKit Trace 之前，需要先了解 visionOS 的渲染管线架构。

一帧画面从代码到屏幕，经过三个独立进程：

1. **应用进程（App Process）**：你的代码在这里运行。SwiftUI 构建视图树，RealityKit 更新实体状态并提交绘制命令。
2. **渲染服务器（Render Server）**：系统的渲染守护进程。它接收所有应用的绘制命令，统一管理 GPU 资源，执行实际的 GPU 渲染。
3. **合成器（Compositor）**：将渲染结果合成到最终显示缓冲区中，应用时间扭曲（Time Warp）补偿头部运动带来的延迟。

应用进程和渲染服务器之间的通信是异步的。你在代码里更新了一个实体的位置，这个更新不会立刻反映到屏幕上。它先被编码为绘制命令，发送给渲染服务器，渲染服务器在下一个可用的 GPU 时间片中执行它，最后由合成器显示。

这种架构意味着两件事：第一，性能瓶颈可能出现在应用进程（CPU 慢）、渲染服务器（GPU 慢）或合成器（合成压力大）的任何一环。第二，在 Shared Space 中，多个应用共享渲染服务器和合成器，其他应用的行为会影响你的帧率。

RealityKit Trace 覆盖了这三个环节。RealityKit Frames 展示应用进程的帧提交节奏和渲染服务器的实际完成时间。RealityKit Metrics 展示渲染服务器内部的 GPU 工作负载分布。

### Shared Space vs Full Space（[02:15](https://developer.apple.com/videos/play/wwdc2023/10099/?time=135)）

测试性能时，两种空间模式要分开测。

**Shared Space（共享空间）**：你的应用和其他应用共存。渲染服务器需要同时处理多个应用的绘制请求，合成器需要合成多个应用的画面。你的应用可能因为别的应用占用了过多 GPU 资源而掉帧。

**Full Space（完全沉浸空间）**：只有你的应用在渲染。这时你能看到应用的性能天花板——在没有任何外部干扰的情况下，它能跑多快。

最佳实践是两种模式都测。先在 Full Space 中找到应用自身的性能瓶颈并修复，然后在 Shared Space 中验证实际用户体验。如果你只在 Full Space 中测试，上线后用户可能在 Shared Space 中遇到完全不同的性能表现。

### 用 RealityKit Frames 定位掉帧（[06:30](https://developer.apple.com/videos/play/wwdc2023/10099/?time=390)）

RealityKit Frames 是定位问题的起点。它的核心界面是一条时间线，每个矩形代表一帧。颜色编码直观：

- **绿色**：帧渲染时间远低于截止线。有充足的余量。
- **橙色**：帧渲染时间接近截止线。虽然赶上了，但几乎没有余量，任何微小的波动都可能导致掉帧。
- **红色**：帧渲染时间超过截止线。这一帧被丢弃了，用户会看到卡顿。

点击任意一帧，可以看到该帧的详细耗时分解：应用进程 CPU 时间、渲染服务器 GPU 时间、合成时间。这让你能快速判断瓶颈在哪个环节。

关键的操作方式：在时间线中框选一段红色密集的区域，然后切换到 RealityKit Metrics 查看该时段的详细指标。不要在全时间线中看平均值——平均值会掩盖偶发的严重掉帧。聚焦在问题时段上。

### 识别 offscreen 渲染问题（[10:50](https://developer.apple.com/videos/play/wwdc2023/10099/?time=650)）

Session 演示中最关键的发现：卡顿不是因为 3D 模型太复杂，而是因为每帧都在做大量不必要的 offscreen 渲染。

示例中有一个带圆角和阴影的 SwiftUI 视图：

```swift
private struct Item: View {
    var module: Module

    let cornerRadius = 20.0

    var body: some View {
        NavigationLink(value: module) {
            VStack(alignment: .leading, spacing: 3) {
                Text(module.eyebrow)
                    .font(.titleHeading)
                    .foregroundStyle(.secondary)
                VStack(alignment: .leading, spacing: 7) {
                    Text(module.heading)
                        .font(.largeTitle)
                    Text(module.abstract)
                }
            }
            .padding(.horizontal, 5)
            .padding(.vertical, 20)
        }
        .buttonStyle(.bordered)
        .shadow(radius: 10)
        .buttonBorderShape(.roundedRectangle(radius: cornerRadius))
        .frame(minWidth: 150, maxWidth: 280)
    }
}
```

关键点：

- `shadow(radius: 10)` 和 `buttonBorderShape(.roundedRectangle(radius: cornerRadius))` 的组合会触发 Core Animation 的离屏渲染路径。系统需要先将视图渲染到一个离屏缓冲区，应用阴影和圆角，再合成到屏幕上。
- 在 visionOS 中，每一帧都可能重新触发这个 offscreen 渲染流程，因为视图可能在空间中移动或与其他内容交互。
- RealityKit Metrics 中的 "Offscreens" 指标直接反映了这个问题——该指标高意味着 GPU 花了很多时间在离屏缓冲区上。

解决方案是避免不必要的 offscreen 渲染。对于静态内容，使用预渲染的纹理替代实时阴影。对于圆角，考虑使用 `clipShape` 配合简单路径，让系统走更快的渲染路径。

### 3D 实体工厂模式（[16:33](https://developer.apple.com/videos/play/wwdc2023/10099/?time=993)）

Session 演示了两种创建 EarthEntity 的方式，它们的性能特征完全不同。

```swift
class EarthEntity: Entity {
    static func makeGlobe() -> EarthEntity {
        EarthEntity(earthModel: Entity.makeModel(
            name: "Earth",
            filename: "Globe",
            radius: 0.35,
            color: .blue)
        )
    }

    static func makeCloudyEarth() -> EarthEntity {
        let earthModel = Entity()
        earthModel.name = "Earth"

        Task {
            if let scene = await loadFromRealityComposerPro(
                named: WorldAssets.rootNodeName,
                fromSceneNamed: WorldAssets.sceneName
            ) {
                earthModel.addChild(scene)
            } else {
                fatalError("Unable to load earth model")
            }
        }

        return EarthEntity(earthModel: earthModel)
    }
}
```

关键点：

- `makeGlobe()` 使用简单的程序化模型——一个蓝色球体，半径 0.35。创建成本极低，没有异步加载。
- `makeCloudyEarth()` 从 Reality Composer Pro 场景加载完整模型。注意它是异步的（`Task` + `await loadFromRealityComposerPro`）——模型加载可能在数帧后才完成。
- 在 RealityKit Trace 中，`makeCloudyEarth()` 的加载过程会显示为一段系统时间飙升，而 `makeGlobe()` 几乎不产生可见的负载。
- 性能建议：对于需要立即显示的场景（如启动画面），使用简单模型。对于高质量展示场景（如近距离观察地球），使用 Reality Composer Pro 的完整模型，但要做好加载中的过渡处理。

### ViewModel 驱动 3D 场景（[17:26](https://developer.apple.com/videos/play/wwdc2023/10099/?time=1046)）

Session 演示了通过 SwiftUI 的 `ObservableObject` ViewModel 来驱动 RealityKit 场景更新。这是一个典型的架构模式。

```swift
class ViewModel: ObservableObject {
    @Published var navigationPath: [Module] = []
    @Published var titleText: String = ""
    @Published var isTitleFinished: Bool = false

    // Globe 状态
    @Published var globeEarthEntity: EarthEntity = .makeGlobe()
    @Published var isShowingGlobe: Bool = false
    @Published var globeEarth: EarthEntity.Configuration = .globeEarthDefault

    // Orbit 状态
    @Published var orbitEarthEntity: EarthEntity = .makeGlobe()
    @Published var isShowingOrbit: Bool = false
    @Published var orbitImmersionStyle: ImmersionStyle = .mixed
    @Published var orbitEarth: EarthEntity.Configuration = .orbitEarthDefault
    @Published var orbitSatellite: SatelliteEntity.Configuration = .orbitSatelliteDefault
    @Published var orbitMoon: SatelliteEntity.Configuration = .orbitMoonDefault
    @Published var orbitSunAngle: Angle = .degrees(150)

    // Solar 状态
    @Published var solarEarthEntity: EarthEntity = .makeCloudyEarth()
    @Published var isShowingSolar: Bool = false
    @Published var solarImmersionStyle: ImmersionStyle = .full
    @Published var solarSunDistance: Double = 700
    @Published var solarSunAngle: Angle = .degrees(280)
}
```

关键点：

- 每个场景（Globe、Orbit、Solar）有独立的状态集。这避免了状态污染——修改 Orbit 的角度不会意外影响 Globe。
- `ImmersionStyle` 控制了场景的沉浸程度：`.mixed` 允许用户同时看到现实世界，`.full` 完全替换用户视野。
- `@Published` 属性每次变化都会触发 SwiftUI 重新评估视图 body。在 RealityKit Trace 中，频繁的 `@Published` 更新会表现为应用进程 CPU 时间的周期性峰值。
- 性能陷阱：如果某个 `@Published` 属性每帧都在变化（比如 `orbitSunAngle` 被 Timer 驱动更新），而该属性的观察者触发了复杂的视图重建，就会导致 CPU 瓶颈。用 RealityKit Metrics 检查 "Entity Updates" 指标来发现这类问题。

### Orbit 视图的 RealityKit 集成（[17:33](https://developer.apple.com/videos/play/wwdc2023/10099/?time=1053)）

```swift
struct Orbit: View {
    @EnvironmentObject private var model: ViewModel

    var body: some View {
        Earth(
            world: model.globeEarthEntity,
            earthConfiguration: model.orbitEarth,
            satelliteConfiguration: [model.orbitSatellite],
            moonConfiguration: model.orbitMoon,
            showSun: true,
            sunAngle: model.orbitSunAngle,
            animateUpdates: true
        )
        .place(
            initialPosition: Point3D([475, -1200.0, -1200.0]),
            useCustomGesture: model.useCustomGesture,
            handOffset: model.customGestureHandOffset,
            isCustomGestureAnimated: model.isCustomGestureAnimated,
            debugCustomGesture: model.debugCustomGesture,
            scale: $model.orbitEarth.scale)
    }
}
```

关键点：

- `Earth` 是一个自定义的 RealityKit 封装视图，接收实体、配置、卫星和月球配置作为参数。它不是标准 SwiftUI 组件，而是将 RealityKit 实体桥接到 SwiftUI 视图层。
- `animateUpdates: true` 告诉 RealityKit 在状态变化时使用动画过渡，而不是突变。这个参数对性能有直接影响——如果为 `true`，每次配置变化都会触发插值动画，增加 CPU 负载。
- `.place()` 修饰符设置 3D 实体的初始空间位置（`Point3D([475, -1200.0, -1200.0])`）。位置以米为单位，这个值表示实体放在用户前方约 1.7 米、下方 1.2 米的位置。
- `scale: $model.orbitEarth.scale` 使用绑定（Binding）实现双向同步——用户手势可以改变缩放比例，而缩放比例的变化会实时反映在 ViewModel 中。
- 在 RealityKit Trace 中，`animateUpdates` 和频繁的 `@Published` 更新组合在一起时，会同时出现在 "Entity Updates" 和 "Animation" 指标中。如果这两个指标都很高，考虑减少动画频率或简化动画路径。

## 核心启发

### 1. 构建一个 3D 模型性能对比工具

**做什么**：写一个 visionOS app，加载同一场景的多个 LOD（细节层次）版本的 3D 模型，用 RealityKit Trace 逐帧对比它们的渲染耗时和 GPU 占用。

**为什么值得做**：RealityKit Metrics 提供了精确到帧的 GPU 时间分解。你可以量化「多 5000 个三角形」对帧率的实际影响，而不是凭感觉判断模型是否「太复杂」。这对 3D 资产制作流程有直接指导意义。

**怎么开始**：创建多个 Entity，分别加载不同面数的模型。用 Timer 每 3 秒切换一次显示。在 Instruments 中启动 RealityKit Trace 模板，录制切换过程，对比不同模型的 "GPU Frame Time" 和 "Entity Updates" 指标。

### 2. 实时性能仪表盘

**做什么**：在 visionOS 应用内叠加一个半透明的性能 HUD，实时显示当前帧率、GPU 利用率和 offscreen 渲染次数。

**为什么值得做**：RealityKit Trace 是事后分析工具，但开发过程中你需要实时反馈。把关键性能指标可视化在应用内，可以在不离开应用的情况下发现性能退化——比如改了某个 View 的 modifier 后帧率突然降到 60fps。

**怎么开始**：使用 `CADisplayLink` 计算实际帧率。结合 RealityKit 的 `arView.session.currentFrame` 获取渲染统计数据。注意不要用 `@Published` 更新 HUD，改用 `@State` 配合 `CADisplayLink` 的 target-action 模式避免额外的 SwiftUI 重绘开销。

### 3. 场景复杂度自动降级

**做什么**：根据 RealityKit Metrics 的实际表现，动态调整场景的渲染质量——当检测到连续掉帧时，自动替换为低面数模型、关闭阴影或降低纹理分辨率。

**为什么值得做**：visionOS 的帧率是动态的（最高 90fps，但系统可能降低到 60fps 或更低）。与其让用户经历卡顿，不如主动降级。Session 中提到的 "System Power Impact" 指标说明功耗是动态变化的——一个场景在冷启动时能跑满 90fps，但运行 5 分钟后可能因为散热限制降到 60fps。

**怎么开始**：用 `CADisplayLink` 监测连续掉帧次数。超过阈值（如连续 3 帧红色）时，调用 `Entity.Configuration` 切换到低质量配置（关闭阴影、减少粒子效果、使用 `makeGlobe()` 替代 `makeCloudyEarth()`）。在 RealityKit Trace 中验证降级前后的功耗差异。

### 4. Shared Space 压力测试工具

**做什么**：创建一个「性能干扰器」app，在 Shared Space 中故意消耗 GPU 资源（渲染大量复杂模型、触发 offscreen 渲染），用来测试你的主 app 在 Shared Space 中的抗干扰能力。

**为什么值得做**：Session 明确提到 Shared Space 中其他应用会影响你的渲染性能。但你无法控制用户同时运行哪些应用。通过模拟最坏情况，你可以确保自己的应用在 Shared Space 中依然流畅。

**怎么开始**：创建第二个 visionOS target，渲染数十个高面数旋转球体（带阴影和半透明材质）。同时运行主 app 和干扰器 app，在 RealityKit Trace 中观察主 app 的帧率变化。调整主 app 的渲染负载直到在干扰下仍保持稳定。

### 5. CI 集成性能回归检测

**做什么**：在 CI 流水线中自动运行 visionOS 应用的性能测试——启动应用、执行关键交互路径、录制 RealityKit Trace、检查平均帧率和红色帧占比是否在可接受范围内。

**为什么值得做**：性能回归往往在代码审查中看不出来。一个看起来无害的 `shadow(radius:)` 可能让特定页面的 offscreen 渲染翻倍。自动化性能测试可以在合并代码之前捕获这类退化。

**怎么开始**：使用 `xcodebuild test` 配合 UI 测试脚本，在模拟器中自动执行关键路径。使用 `xctrace` 命令行工具录制 RealityKit Trace 模板（`xctrace record --template 'RealityKit Trace' --output trace.trace`）。解析输出文件中的帧率统计，设置阈值告警。
