## Highlight

> Apple GPU 软件工程团队的 Marco Giordano 演示了如何从 8 核 M1 到 64 核 M1 Ultra 实现接近线性的性能扩展。核心问题不是 GPU 太慢，而是工作分布不均、时间线空闲间隙、内存访问模式未优化。Blender Cycles 渲染器的优化案例展示了从 40% GPU 利用率提升到接近饱和的完整路径。

---

## 核心内容

Apple silicon 的 GPU 扩展能力很强——从 M1 的 8 核到 M1 Ultra 的 64 核，理论上是 8 倍性能。但现实中很多 workload 在不同芯片上跑出来的性能曲线远低于线性，甚至出现平台期。

这场 session 的核心诊断框架是三问：
1. **GPU 是否在满负荷工作？** 看 Instruments 的 GPU track，有没有空闲间隙。
2. **工作是否均匀分布？** 每个 GPU 核拿到的任务量是否相当。
3. **瓶颈在哪？** 计算受限还是带宽受限，内存访问模式是否合理。

优化分两步走：先消除 GPU 空闲（改善工作分布、减少 CPU/GPU 同步、注意原子操作开销），再突破性能瓶颈（调整 grid 形状、优化内存布局）。

Blender Cycles 的案例展示了从 40% 利用率到接近饱和的过程：一开始是 GPU 大部分时间在等 CPU，原因是工作拆分粒度太粗、同步点太多；调整并发 dispatch 尺寸、减少 waitUntilCompleted 调用、用 Shared Event 建立异步依赖后，GPU 时间线填满了；最后再优化内存访问模式，突破带宽瓶颈。

## 详细内容

### 问题 1：GPU 时间线有空闲间隙

（[02:15]([https://developer.apple.com/videos/play/wwdc2022/10159/?time=135)）GPU 被设计成始终在工作的状态：它从 command queue 拿任务，执行完再拿下一个。如果队列空了，GPU 就进入空闲状态，这就是浪费。

空闲间隙的来源通常是 CPU 和 GPU 之间的同步点。最明显的是 `waitUntilCompleted` 调用——CPU 会停下等 GPU 跑完当前工作，然后再提交下一批。这种串行模式会让 GPU 在等待期间无事可做。

更好的方式是用 Shared Event 建立 GPU 内部的依赖：前一个 dispatch 结束时 signal 这个 event，后一个 dispatch 开始前 wait 这个 event。两个 dispatch 可以在同一个 command buffer 里，事件依赖由 GPU 自己处理，CPU 不需要插手。

另一个常见场景是并发 dispatch 的粒度太粗。比如你有 100 万个元素要处理，结果只 dispatch 了 10 次，每次处理 10 万个元素。GPU 上只有 10 个 workgroup 在跑，大量核心闲置。把 dispatch 次数增加到 1000 次，每次 1000 个元素，GPU 上的并发度就能上来。

经验值：目标是每个 GPU 核心上有 1K-2K 个并发线程。8 核 GPU 上至少要 8K-16K 个线程，64 核上要 64K-128K。dispatch 的 threadgroup 数量和每个 threadgroup 的线程数相乘要落在这个范围内。

### 问题 2：工作分布不均匀

（[08:30]([https://developer.apple.com/videos/play/wwdc2022/10159/?time=510)）工作不均匀意味着部分 GPU 核忙死，部分核闲死。这通常发生在 workload 本身有倾斜时——比如有些元素的计算量特别大，有些特别小。

Blender Cycles 的案例很典型：光线追踪渲染时，某些像素需要追踪上百次光线才能收敛，某些像素几十次就够。如果按像素平均分配工作，某些 GPU 核会被重负载像素卡住，其他核早就跑完剩下的轻量像素也帮不上忙。

解决方案是动态任务调度。维护一个全局的任务池，GPU 核完成当前任务后自己去取下一个。这样重负载任务会被多核分摊，轻负载任务也不会让核闲置。

Metal 提供了 atomic operations 来实现这种模式。可以用 atomic counter 来跟踪任务队列的当前位置，每个 workgroup 完成任务后 atomic add 取下一批。这种方式需要权衡：atomic 操作本身有开销，但比让核闲置强。

### 问题 3：计算或带宽瓶颈

（[15:45]([https://developer.apple.com/videos/play/wwdc2022/10159/?time=945)）GPU 时间线填满后，下一步是突破性能瓶颈。瓶颈分两种：计算受限（compute-bound）和带宽受限（bandwidth-bound）。

计算受限意味着 GPU 的计算单元已经满负荷，算力是天花板。这种情况下的优化方向是减少不必要的计算、用更低精度的浮点（比如 half 而不是 float）、利用 SIMD 指令。

带宽受限意味着 GPU 等内存数据供应。内存访问模式在这里很关键：连续访问比随机访问快得多，因为内存控制器可以预取和合并请求。struct of arrays（SoA）比 array of structs（AoS）更友好，因为同类型数据在内存里连续。

Instruments 的 Metal Performance Counters 可以帮你诊断瓶颈类型。如果看到 ALU time 很高，就是计算受限；如果看到 Memory traffic 很高但 ALU time 低，就是带宽受限。

### 工具链：Xcode 和 Instruments

（[20:10]([https://developer.apple.com/videos/play/wwdc2022/10159/?time=1210)）Xcode 的 Metal Debugger 可以让你单步调试 shader，查看每个 thread 的寄存器状态。Instruments 的 GPU Track 可以显示 GPU 的时间线和利用率，Metal Performance Counters 则提供更细粒度的硬件指标。

关键计数器包括：
- **GPU utilization**：实际工作时间占比
- **ALU time**：计算单元利用率
- **Memory traffic**：内存带宽使用量
- **Vertex/Fragment throughput**：几何和像素处理吞吐

这些工具可以帮助你定位问题阶段。先用 GPU Track 看宏观利用率，再用 Performance Counters 找瓶颈类型，最后用 Metal Debugger 下钻到具体 shader 代码。

## 核心启发

- **GPU 利用率是第一优先级。** 在优化任何具体算法前，先确保 GPU 一直在做事。空闲间隙就是浪费。
- **同步点是敌人。** 能用 Shared Event 的地方不要用 CPU 端的 wait，能把依赖编码进 command buffer 的地方不要用 barrier。
- **工作粒度要适配硬件。** 粗粒度会让核闲置，细粒度会增加调度开销。1K-2K 线程/核是经验起点。
- **瓶颈诊断要有数据。** 靠猜测会走弯路。用 Instruments 的计数器确定瓶颈类型，再针对性优化。
