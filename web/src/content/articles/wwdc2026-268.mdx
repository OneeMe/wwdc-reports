## 核心内容

### 1. 这场演讲解决什么问题

App 卡顿是开发者永远的痛，但排查卡顿往往靠直觉和经验：

- Time Profiler 的 Call Tree 像天书，层层展开才能找到热点
- Swift Concurrency 普及后，Main Actor 被隐式占用导致 UI 掉帧成了新灾区
- 有些卡顿发生时 CPU 是闲置的（等锁、等文件 I/O），Time Profiler 完全看不到
- 优化后没有系统的方法验证效果，只能凭感觉

Instruments 27 的解法是：**给一套标准化诊断流程，让每个开发者都能像性能专家一样排查问题。**

### 2. 诊断心智模型：四步工作流

当 App 掉帧或卡顿时，按这个顺序排查：

**Step 1: Time Profiler — 判断问题类型**

- 如果卡顿时 **CPU 飙高** → 代码执行太慢，需要优化算法或把任务移出主线程
- 如果卡顿时 **CPU 闲置** → 主线程在等待资源（I/O、锁、IPC），需要排查阻塞原因

**Step 2: Top Functions — 找到最耗时的代码**

Instruments 27 新增的 Top Functions 视图把最耗时的函数直接平铺展示，不需要一层层展开调用栈。一眼就能看到哪个函数在吃 CPU。

**Step 3: Swift Concurrency Instrument — 查执行争用**

如果用了 Swift Concurrency 但主线程仍然卡顿，检查：

- 是否有大量任务同时竞争 Main Actor
- `await` 调用是否意外地阻塞了主线程
- Task 的优先级设置是否合理

**Step 4: System Trace — 查系统阻塞**

CPU 闲置时的卡顿，用 System Trace 看：

- 文件 I/O 等待
- 同步锁竞争
- 进程间通信阻塞
- 内存分配压力

### 3. 用 OSSignpost 标记关键路径

在代码中插入 Signpost，让 Instruments 显示业务语义的时间线：

```swift
import os.signpost

let signposter = OSSignposter(subsystem: "Demo App", category: .pointsOfInterest)
var lassoIntervalState: OSSignpostIntervalState? = nil

func lassoSelectionUpdated() {
    lassoIntervalState = signposter.beginInterval("Lasso Selection")
    // 更新选区...
}

func lassoSelectionEnded() {
    // 完成选区...
    signposter.endInterval("Lasso Selection", lassoIntervalState!)
}
```

配合文件保存操作：

```swift
// 优化前：在主线程同步写文件
let encoder = PropertyListEncoder()
encoder.outputFormat = .binary
guard let data = try? encoder.encode(snapshots) else { return }
let id = signposter.beginInterval("Writing To File")
try? data.write(to: fileURL, options: .atomic)
signposter.endInterval("Writing To File", id)

// 优化后：移到后台线程
Task { @concurrent in
    let encoder = PropertyListEncoder()
    encoder.outputFormat = .binary
    guard let data = try? encoder.encode(snapshots) else { return }
    let id = signposter.beginInterval("Writing To File")
    try? data.write(to: fileURL, options: .atomic)
    signposter.endInterval("Writing To File", id)
}
```

### 4. 优化 Swift Concurrency 代码

**把耗时操作移出 Main Actor**：

```swift
// 优化前：在主 Actor 上渲染缩略图
let drawingData = note.drawingData
let canvasImages = note.decodeCanvas()
thumbnail = await Task(name: "Render Thumbnail") {
    await renderThumbnail(drawingData: drawingData, canvasImages: canvasImages, size: CGSize(width: 300, height: 240))
}.value

// 优化后：标记为 @concurrent，明确不在 Main Actor 上执行
thumbnail = await Task(name: "Render Thumbnail") { @concurrent in
    await renderThumbnail(drawingData: drawingData, canvasImages: canvasImages, size: CGSize(width: 300, height: 240))
}.value
```

**用具体类型替代 Existentials 提升性能**：

```swift
// 慢：Existential（运行时动态分发）
protocol Foo { }
struct TypeA: Foo { }
struct TypeB: Foo { }
func bar(_ foo: any Foo) { }

// 快：具体类型（编译器静态分发）
func bar(_ a: TypeA) { }
func bar(_ b: TypeB) { }

// 更快：泛型（编译器单态化）
func bar<T: Foo>(_ generic: T) { }

// 最快：枚举（无动态分发）
enum Foo {
    case a(TypeA)
    case b(TypeB)
}
```

### 5. Run Comparison 验证优化效果

Instruments 27 支持把两次 Profiling 结果并排对比：

- 优化前的 trace 作为 baseline
- 优化后的 trace 与之对比
- 直接看到每个函数的执行时间变化
- 确认卡顿是否真正消除，而不是被其他问题掩盖

## 最佳实践

- **永远用 Release 构建跑 Profiling**：Debug 模式关闭了编译器优化并插入大量运行时检查，测出来的数据毫无参考价值
- **先用 Time Profiler 定位方向**：CPU 高 → 优化算法或移出主线程；CPU 低 → 切 System Trace 查阻塞
- **全面使用 OSSignpost**：把网络请求、数据库查询、复杂 UI 渲染等关键路径用 Signpost 包起来，Instruments 里能看到业务语义的时间线
- **优化后用 Run Comparison 验证**：不要凭感觉说"应该快了"，用数据证明
- **Existentials 是性能陷阱**：协议类型的 `any Foo` 有运行时开销，性能敏感路径用具体类型、泛型或枚举替代
