## Highlight

> 这场 Code-along 手把手演示了如何把 SwiftUI 日历 App 接入 Siri。通过 App Schemas 把数据"贴"到系统预定义的 Domain 上，不需要写训练短语，按着 Xcode 代码补全一天就能搞定以前一周的 Siri 适配工作。

---

## 核心内容

### 1. 这场演讲解决什么问题

以前要让 Siri 听懂 App 里的业务，得在 SiriKit 里配一堆 Intent 定义文件，还得手写各种训练短语祈祷 NLP 模型能猜对用户的意思。现在 Apple Intelligence 接管了大脑，开发者只需要用 App Schemas 把数据结构和动作"贴"到系统预定义的 Domain 上。

这场 Code-along 以一个 SwiftUI 日历 App (CometCal) 为例，演示了完整的接入流程。

### 2. 用 App Schemas 定义实体

App Schemas 按 Domain 组织，日历 Domain 覆盖事件、日历、参与者等。在 Xcode 里输入 `calendar_`，自动补全会列出所有可用的 Schema。

```swift
import AppIntents

// 给 Calendar 数据模型创建 Siri 可理解的实体
@AppEntity(schema: .calendar.calendar)
struct CalendarEntity: IndexedEntity {
    var id: String
    var title: String
    var color: Color
    
    static let defaultQuery = CalendarQuery()
    
    var displayRepresentation: DisplayRepresentation {
        DisplayRepresentation(title: title, image: .init(systemName: "calendar"))
    }
}
```

`@AppEntity(schema: .calendar.calendar)` 告诉 Siri 这个实体属于日历类别。`IndexedEntity` 协议让内容自动进入 Spotlight 语义索引，用户可以直接搜"下周的野餐"。

### 3. 定义查询 (Query)

Query 负责把系统请求翻译成你的数据层操作：

```swift
struct CalendarQuery: EntityQuery {
    func entities(for identifiers: [CalendarEntity.ID]) async throws -> [CalendarEntity] {
        // 根据 ID 从 SwiftData/Core Data 获取日历
        return try await CalendarModel.fetch(byIDs: identifiers)
            .map { CalendarEntity($0) }
    }
    
    func suggestedEntities() async throws -> [CalendarEntity] {
        // 返回用户常用的日历，用于 Siri 建议
        return try await CalendarModel.all().map { CalendarEntity($0) }
    }
}
```

### 4. 用 Schema Intent 定义动作

不需要从零定义 Intent，直接用日历 Domain 预定义的动作 Schema：

```swift
@AppIntent(schema: .calendar.createEvent)
struct CreateEventIntent {
    @Parameter var title: String
    @Parameter var startDate: Date
    @Parameter var endDate: Date?
    @Parameter var calendar: CalendarEntity?
    
    func perform() async throws -> some ReturnsValue<EventEntity> {
        let calendarID = calendar?.id ?? CalendarModel.defaultCalendarID
        let event = try await CalendarModel.createEvent(
            title: title,
            startDate: startDate,
            endDate: endDate,
            calendarID: calendarID
        )
        return .result(value: EventEntity(event))
    }
}
```

### 5. 屏幕感知 (Onscreen Awareness)

让 Siri 知道用户正在看什么，才能理解"把这个移到 11:30"里的"这个"：

```swift
struct EventDetailView: View {
    let event: Event
    
    var body: some View {
        VStack {
            Text(event.title)
            Text(event.dateRange)
            // ...
        }
        .appEntityIdentifier(
            EntityIdentifier(for: EventEntity.self, identifier: event.id)
        )
    }
}
```

### 6. 处理不需要独立搜索的子实体

参与者 (Attendee) 这种依附于事件的实体，用 `TransientAppEntity` 而不是 `IndexedEntity`：

```swift
@AppEntity(schema: .calendar.participant)
struct AttendeeEntity: TransientAppEntity {
    var id: String
    var name: String
    var email: String?
    
    var displayRepresentation: DisplayRepresentation {
        DisplayRepresentation(title: name)
    }
}
```

Transient 实体不会进入 Spotlight 索引，但 Siri 可以在处理事件相关的 Intent 时引用它们。

## 最佳实践

- **已有项目的迁移策略**：别想着一次性把所有业务都接进 App Schemas。先挑出最核心的"名词"（如订单、文章、日程），给它们加上 `IndexedEntity` 并接入 Spotlight。跑通搜索后，再挑最高频的"动词"（如创建、打开）做 Intent。
- **新项目的采用建议**：在数据模型设计阶段就引入 `@AppEntity`。把 App Intents 的 Entity 作为你领域模型的一等公民，而不是在 UI 层写完后再去硬写一层转换代码。利用 Xcode 的 Snippets（输入 `calendar_` 等前缀）来生成 Schema。
- **实战避坑**：屏幕感知非常依赖 View 的层级。如果你的详情页被包在自定义的 `NavigationStack` 或复杂的 `TabView` 里，`.userActivity` 可能会因为视图未完全渲染或失去焦点而丢失上下文。建议在真实的 Siri 语音环境下多测几次"这个"、"那个"的指代。
