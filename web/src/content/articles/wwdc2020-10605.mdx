## Highlight

> Xcode 12 在 Metal Debugger 和 Instruments 中加入 Summary、Insights、Shader Timeline 与 Performance Limiter 轨道，让开发者能从一次 frame capture 找到带宽浪费、冗余 pass 和 shader 执行热点。

## 核心内容

一个复杂 Metal app 的问题，往往不是“画错了”这么简单。真实项目里，一个 frame 可能有几十个 render command encoder、上千次 draw call、多个中间 texture。画面能显示，不代表 GPU 花的时间和带宽是合理的。

以前排查这类问题，开发者需要先知道 Apple GPU 的架构，再从大量 command buffer、encoder、counter 里猜问题。新手很容易停在第一步：我知道 frame 很慢，但不知道该先看内存、shader，还是 render pass 依赖。

这场 session 的核心变化，是 Xcode 12 把 Metal Debugger 和 Metal System Trace 变成了更有指向性的工作流。Metal Debugger 负责单帧。Instruments 的 Metal System Trace 负责一段时间内的运行状态。前者回答“这一帧哪里浪费了”，后者回答“运行时为什么卡顿、掉帧或泄漏”。

Apple 用《Divinity: Original Sin 2》的 iPad 版本做示例。这个 frame 有 4 个 command buffer、53 个 render command encoder、接近 1000 次 draw call，渲染时间约 26ms。Xcode 的 Insights 直接指出两个问题：一个 depth/stencil 资源被 store 后没有再使用，另一个 depth pre-pass 在 Apple GPU 上可以省掉。

## 详细内容

### Summary View：先看一帧的总览

（[01:22](https://developer.apple.com/videos/play/wwdc2020/10605/?time=82)）Metal Debugger 的入口仍然是 frame capture。开发者先在 Xcode scheme 里启用 GPU Frame Capture，运行 Metal app，在想分析的画面点击 debug bar 里的相机按钮。

Xcode 12 新增的 Summary View 把 encoder 概览、性能数字、内存使用放到同一页。它还提供 Insights，提示哪些地方可能影响 memory usage、bandwidth、performance 或 Metal API usage。每条 Insight 都带有问题描述、修复提示和文档链接。

```text
Metal Debugger 单帧排查顺序
1. Enable GPU Frame Capture
2. Run the Metal app
3. Click the camera icon at the target frame
4. Open Summary View
5. Read Overview, Performance, Memory, and Insights
6. Jump from an Insight to the matching tool
```

关键点：

- `Enable GPU Frame Capture` 是入口，目标是获得一个可重复检查的单帧快照。
- `Summary View` 把 frame 的关键指标集中到一处，避免先在多个面板之间盲找。
- `Insights` 不只显示现象，还给出可执行修复方向。
- `Jump from an Insight` 是这套工具的重点：从问题直接进入 Dependency Viewer、Memory Viewer 或其他相关工具。

### Dependency Viewer：看清 encoder 和资源依赖

（[02:23](https://developer.apple.com/videos/play/wwdc2020/10605/?time=143)）Dependency Viewer 可以从 Summary View 的 Show Dependencies 进入，也可以从 navigator 里的 command buffer 或 encoder 进入。它给出所有 GPU pass 的鸟瞰图，适合检查 load/store action 和带宽问题。

在示例项目里，Insights 提示某个 encoder store 了一个后续没有使用的资源。Dependency Viewer 显示 depth texture 和 stencil texture 都被设置为 Store，但图上没有从它们连出去的依赖线。Xcode 因此建议把 store action 改成 Don't Care。这个改动可以节省接近 11MB memory bandwidth。

```text
Bandwidth Insight 示例
Resource: depth texture + stencil texture
Current action: Store
Observed dependency: no outgoing use in this frame
Suggested action: Don't Care
Estimated saving: almost 11 MB memory bandwidth
```

关键点：

- `Store` 表示 render pass 结束后要把结果写回，代价是内存带宽。
- `no outgoing use` 说明这一帧后面没有 encoder 读取这些 depth/stencil 结果。
- `Don't Care` 适合这种后续不再使用的 attachment，工具给出的收益是减少约 11MB 带宽。
- 这里的判断来自 Dependency Viewer 的资源依赖线，不是凭经验删除 store。

### Shader Profiler 与 Shader Debugger：把 shader 问题落到源码行

（[03:34](https://developer.apple.com/videos/play/wwdc2020/10605/?time=214)）对于 shader，Xcode 提供两条路径。切到 “View Frame by Pipeline State”，选择 render pipeline 后，Shader Profiler 可以在 Apple GPU 上给出 shader source code 的逐行性能分解。开发者还可以在 profiler 里直接编辑 shader，观察性能变化。

（[04:04](https://developer.apple.com/videos/play/wwdc2020/10605/?time=244)）Shader Debugger 则从 debug bar 的 debug button 进入。开发者可以选择 pixel 调 fragment shader，选择 geometry 调 vertex shader，选择 threads 调 compute shader。调试器会展示多线程执行过程中的变量状态，并允许查看整个 shader 执行期间的值。

```text
Shader Debugger 入口
- Pixel: debug the fragment shader
- Geometry: debug the vertex shader
- Threads: debug a compute shader

Shader Debugger 能力
- inspect variable state over multiple threads
- inspect values across the entire shader execution
- edit shader source and see live changes
```

关键点：

- `Pixel` 对应 fragment shader，适合分析某个像素为什么得到当前颜色。
- `Geometry` 对应 vertex shader，适合检查顶点阶段的输入和输出。
- `Threads` 对应 compute shader，适合定位计算核里的线程状态。
- `entire shader execution` 解决了传统单步调试中“走过头不能回看”的问题。
- `edit shader source` 让开发者在调试阶段快速验证假设，不需要完整回到工程重新构建。

### Metal System Trace：看运行过程里的卡顿和泄漏

（[06:27](https://developer.apple.com/videos/play/wwdc2020/10605/?time=387)）Metal Debugger 看单帧，Metal System Trace 看一段时间。它是 Instruments 里的 template，适合定位 stutter、dropped frames、memory leaks 这类时间相关问题。Game template 还提供了一组适合游戏分析的 track。

Encoder Timeline 在 GPU track 下展示 command buffer 的时间线，并按 frame 着色。开发者可以检查 encoder 之间是否有重叠，GPU 是否出现 idle bubble，还可以把 GPU 状态和其他系统 track 关联起来。例如 encoder 变慢时，旁边的 thermal state 可能已经进入 critical。

```text
Metal System Trace 观察点
- Encoder Timeline: command buffers over time, color-coded by frame
- Shader Timeline: sampled shaders during a command encoder
- Performance Limiter tracks: limiter values over time
- Memory Allocations: buffer and texture allocation / deallocation
```

关键点：

- `Encoder Timeline` 适合看 GPU 是否连续工作，或者是否有空泡。
- `Shader Timeline` 需要在 Metal Application recording options 中启用，它显示 command encoder 执行期间被采样到的 shader。
- `Performance Limiter tracks` 通过 GPU Counter Set 启用，展示 limiter 随时间变化的值。
- `Memory Allocations` 展示 buffer 和 texture 的分配、释放时机，用于排查泄漏或降低 footprint。

### 用 Insights 找到冗余 depth pre-pass

（[11:49](https://developer.apple.com/videos/play/wwdc2020/10605/?time=709)）示例中的第二个问题来自 Performance category。Xcode 提示某个 render command encoder 可能是不必要的 depth pass。这个 encoder 花了 1.71ms GPU time，处理约 100 万个 vertices，thumbnail 显示它把整个场景画进 depth/stencil texture。

Dependency Viewer 进一步显示，这个结果随后被另一个 encoder 使用，而后者又绘制了整个场景。演讲者判断它很像传统 depth pre-pass。对非 Apple GPU，这种技术常用于减少 overdraw。对 Apple GPU，Tile Based Deferred Rendering 架构会自动做 hidden surface removal，所以这个 pass 可以移除，节省 1.71ms GPU time。

```text
Performance Insight 示例
Encoder cost: 1.71 ms GPU time
Geometry: roughly 1 million vertices
Pattern: render whole scene into depth/stencil textures
Follow-up pass: draw the whole scene again
Reason to remove: Apple GPUs perform hidden surface removal
Potential saving: 1.71 ms GPU time
```

关键点：

- `1.71 ms GPU time` 是 Xcode 从 frame capture 中给出的具体成本。
- `roughly 1 million vertices` 说明这个 pass 不是小开销。
- `draw the whole scene again` 暗示它是 depth pre-pass，而不是独立效果 pass。
- `hidden surface removal` 是 Apple GPU 架构已经提供的能力，减少了手写 depth pre-pass 的必要性。

## 核心启发

1. **做一个 frame capture 健康检查面板**
   - **做什么**：给团队内部建立固定流程，每次大版本前抓取关键场景的一帧，记录 command buffer 数量、encoder 数量、draw call 数量、frame time 和 Insights。
   - **为什么值得做**：session 示例里，Summary View 一眼暴露了 26ms frame、53 个 render encoder 和接近 1000 次 draw call。
   - **怎么开始**：从 Xcode 的 GPU Frame Capture 开始，把 Summary View 的 Overview、Performance、Memory 和 Insights 作为检查项。

2. **做一个 bandwidth 回归清单**
   - **做什么**：专门检查 depth、stencil、color attachment 的 store action，找出 Store 后没有后续使用的资源。
   - **为什么值得做**：示例里只改一个 depth/stencil store action，就能节省接近 11MB memory bandwidth。
   - **怎么开始**：在 Dependency Viewer 里从 Insights 跳转到对应 encoder，确认资源是否有 outgoing dependency，再把无用 Store 改成 Don't Care。

3. **做一个 Apple GPU 专用渲染路径审计**
   - **做什么**：审查从其他 GPU 架构继承来的 depth pre-pass、overdraw 规避 pass 和中间 texture 写回策略。
   - **为什么值得做**：Apple GPU 的 hidden surface removal 让某些传统 depth pre-pass 失去价值，示例中移除一个 pass 可节省 1.71ms GPU time。
   - **怎么开始**：用 Performance Insights 找到高成本 depth pass，再用 thumbnail popover 和 Dependency Viewer 判断是否重复绘制整场景。

4. **做一个卡顿调查模板**
   - **做什么**：当玩家反馈 stutter 或 dropped frames 时，用 Instruments 的 Metal System Trace 捕捉一段过程，而不是只看单帧。
   - **为什么值得做**：Metal System Trace 可以把 Encoder Timeline、thermal state、Shader Timeline、Performance Limiter 和 Memory Allocations 放在同一条时间线上。
   - **怎么开始**：用 Game template 录制复现场景，先看 GPU track 有没有 idle bubble，再打开 Shader Timeline 和 Performance Limiter tracks。

5. **做一个 shader 热点修复循环**
   - **做什么**：把 shader 性能问题拆成“哪条源码行慢”和“哪个变量状态错”两个问题处理。
   - **为什么值得做**：Shader Profiler 给出逐行性能分解，Shader Debugger 可以查看多个线程、整个执行过程的变量值。
   - **怎么开始**：在 frame capture 里切到 View Frame by Pipeline State，选择 render pipeline；性能问题进 Shader Profiler，结果错误进 Shader Debugger。
