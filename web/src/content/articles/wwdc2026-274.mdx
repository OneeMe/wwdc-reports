## Highlight

> SwiftData 今年终于把数据监听能力从 SwiftUI 视图层解放出来了。`ModelResultsObserver` 让任意 Swift 代码都能监听查询结果变化，`HistoryObserver` 支持精确追踪数据变更历史。同时 `@Query` 原生支持 `sectionBy` 分组，`@Attribute(.codable)` 让第三方类型直接入库——MVVM 架构下数据层和视图层终于可以彻底解耦。

---

## 核心内容

### 1. 这场演讲解决什么问题

SwiftData 推出两年来，开发者遇到几个结构性痛点：

- `@Query` 只能用在 SwiftUI `View` 里，非 UI 层（ViewModel、Service）想监听数据变化只能写 Notification 桥接
- 带 Section 的列表需要自己手写 Dictionary 分组逻辑
- 第三方库的类型（如 MapKit 的 `MKMapItem.Identifier`）无法直接存入 SwiftData
- 后台同步服务无法精确追踪哪些数据发生了变更

今年的更新一次性解决了这些问题。

### 2. Sectioned Fetching：原生分组查询

以前要实现按目的地分组的旅行列表，需要手动写分组逻辑：

```swift
// 现在：一行代码搞定分组
struct TripListView: View {
    @Query(sort: \Trip.startDate, sectionBy: \.destination)
    var trips: [Trip]

    var body: some View {
        List(selection: $selection) {
            ForEach(_trips.sections) { section in
                Section(section.id) {
                    ForEach(section) { trip in
                        TripListItem(trip: trip)
                    }
                }
            }
        }
    }
}
```

关键点：

- `sectionBy:` 参数传入 KeyPath，按该属性自动分组
- 通过 `_trips.sections` 访问分组结果（下划线前缀访问 property wrapper 本身）
- 每个 section 的 `id` 就是分组属性的值（这里是 `destination`）
- 内层 `ForEach` 遍历 section 内的元素

### 3. Codable 属性：第三方类型直接入库

SwiftData 自动生成 schema 时，无法处理未标记 `@Model` 的 class 类型。但许多第三方库的类型是 class 且符合 `Codable`：

```swift
import SwiftData

@Model class Trip {
    struct Location: Codable {
        var latitude: Double
        var longitude: Double
    }

    var name: String
    var destination: String
    var startDate: Date
    var endDate: Date

    var location: Location?
    @Attribute(.codable) var mapItemIdentifier: MKMapItem.Identifier?
}
```

关键点：

- `@Attribute(.codable)` 告诉 SwiftData：这个属性用 Codable 序列化存储
- 适用于第三方库的 class 类型（如 MapKit、Core Location 的类型）
- 不需要写自定义 `ValueTransformer` 或 `Transformable`
- 数据以二进制形式存储，读取时自动反序列化

### 4. ModelResultsObserver：任意代码监听数据变化

`@Query` 只能用在 View 里。`ModelResultsObserver` 让任意 Swift 代码都能监听查询结果：

```swift
@Observable @MainActor final class MapCameraController {
    private let modelResultsObserver: ModelResultsObserver<Trip>
    var bounds: MapCameraBounds?
    private var token: ObservationTracking.Token?

    init(modelContext: ModelContext) throws {
        modelResultsObserver = try ModelResultsObserver<Trip>(modelContext: modelContext)

        token = withContinuousObservation(options: [.didSet]) { [weak self], event in
            self?.bounds = self?.calculateBounds(trips: modelResultsObserver.results)
        }
    }

    private func calculateBounds(trips: [Trip]) -> MapCameraBounds? { /* ... */ }
}
```

关键点：

- `ModelResultsObserver` 不依赖 SwiftUI，可以在 ViewModel、Service 等任意地方使用
- `withContinuousObservation` 持续监听结果变化
- `.didSet` 选项在值变化时触发回调
- `[weak self]` 避免循环引用
- 数据变化时自动更新 `MapCameraBounds`，驱动地图视图调整

### 5. HistoryObserver：精确追踪变更历史

后台同步服务需要知道哪些数据发生了变化，以便同步到服务器：

```swift
@SyncActor final class ServerSync {
    private let observer: HistoryObserver
    private var token: ObservationTracking.Token?

    func start() throws {
        self.observer = try HistoryObserver(
            authors: ["App"],  // 只监听本 App 产生的变更
            modelContainer: modelContainer
        )
        token = withContinuousObservation(options: .didSet) { [weak self] _ in
            _ = self?.observer.eventCounter
            self?.processChanges()
        }
    }

    private func processChanges() {
        // 获取并处理历史事务
        // 只推送本 App 产生的变更到服务器
        // 避免把服务器拉取的数据再次推回去（死循环）
    }
}
```

关键点：

- `HistoryObserver` 追踪数据存储的变更历史
- `authors` 参数过滤变更来源，避免同步死循环
- 配合 `withContinuousObservation` 实时响应变更
- 适用于云端同步、数据备份、审计日志等场景

## 最佳实践

- **把数据获取逻辑从 View 层抽离**：简单列表用 `@Query`，复杂场景用 `ModelResultsObserver` 放在 ViewModel 里
- **删除 Notification 桥接代码**：之前用 `NSManagedObjectContextDidSave` 或隐藏 SwiftUI View 桥接的，全部替换为 `ModelResultsObserver`
- **第三方类型优先用 `@Attribute(.codable)`**：比写 `ValueTransformer` 简单得多
- **HistoryObserver 必须传 `authors`**：做云端同步时过滤变更来源，否则会导致数据死循环
- **sectionBy 配合 OrderedCollections**：如果需要在分组后做复杂排序，结合 swift-collections 的 `OrderedDictionary`
