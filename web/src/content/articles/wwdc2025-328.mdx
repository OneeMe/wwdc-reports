## Highlight

> App Store Connect 这一年的重点是「让用户在下载前就判断这个 app 适不适合自己」：Accessibility Nutrition Labels、Review Summaries、5 档年龄分级、CPP 关键词搜索一起上线。

## 核心内容

过去几年，开发者上传 build 失败后最痛的一件小事：那个 build number 就废了。下次得重新递增版本号，CI 脚本和发版记录全乱。这次 Apple 干脆把「上传过程」单独抽出来。TestFlight 区域多了一个 Build Uploads 板块，build 在交付过程中实时显示状态——从创建、processing 到完成或失败。失败的 build 不再被丢弃，会保留在列表里，错误信息和 warning 都查得到。最重要的是，**失败的 build number 可以重用**（[02:38](https://developer.apple.com/videos/play/wwdc2025/328/?time=158)）。配合即将上线的 App Store Connect API 上传能力和 webhook 实时通知，整条交付流水线终于能完全自动化。

另一个长期被吐槽的环节是「App Store 怎么让用户找到我」。Apple 的回应是 App Store Tags：用大语言模型扫你的 app metadata（描述、分类、截图），自动生成更细粒度的标签，再走人工审核。用户点击 tag 进入策划好的专题页，开发者在 ASC 的 App information 里能看到自己的 tag 列表，可以取消那些不准确的关联（[09:56](https://developer.apple.com/videos/play/wwdc2025/328/?time=596)）。同时 Custom Product Page 终于能在搜索结果里出现——给每个 CPP 分配关键词，搜该词时展示对应 CPP 而非默认产品页，**不用提交审核就能上线**（[11:36](https://developer.apple.com/videos/play/wwdc2025/328/?time=696)）。

## 详细内容

整场 session 由 Chinedu 和 Michael 分四块讲，每一块都对应一个具体痛点。

**1. 管理 App（Michael）**

Build Uploads 板块替代了过去那种「失败后什么都看不到」的体验。从 build delivery 创建、processing 到完成，每一步状态都展示出来；同名版本号 + build number 的失败记录和成功记录会并列显示（[03:19](https://developer.apple.com/videos/play/wwdc2025/328/?time=199)）。配合：

- App Store Connect API 上传能力（今年晚些时候）
- Webhooks 推送 build 状态变化
- TestFlight Feedback 也走 webhook 和新的 feedback API

App Store Connect iPhone/iPad app 现在能直接收到 TestFlight feedback 推送（截图 + crash log），支持 digest 模式避免被通知淹没，可以从手机上一键把 feedback 分享给团队成员（[06:30](https://developer.apple.com/videos/play/wwdc2025/328/?time=390)）。Apple-Hosted Background Assets 提供最高 200GB 的 Apple 托管资源包，覆盖 Mac/iPhone/iPad/Apple TV/Vision Pro，可以在 app 之外更新内容（[04:15](https://developer.apple.com/videos/play/wwdc2025/328/?time=255)）。

**2. 帮用户发现你的 App（Chinedu）**

App Store Tags、CPP 关键词、Offer Codes 三件套。其中 CPP 关键词的配置路径很短，session 里现场演示了一遍：

```text
App Store Connect
  └─ App information
       └─ 查看 Tags（可点 Edit 取消不准确的 tag）

App Store Connect
  └─ Custom Product Pages
       └─ 选中目标 CPP（例：workouttracking）
            └─ 从最新 App Store 版本的关键词中选取一个或多个
                 └─ 按语言分别配置
                      └─ 保存即生效，无需重新提交审核
```

关键点：

- 取消一个 App Store Tag = 该 tag 对应的策划页不再展示你的 app，搜索结果里也拿不到这个入口。
- CPP 关键词只能从你已提交的 App Store 版本关键词里选，不能凭空写一个新词。
- CPP 关键词命中后，搜索结果展示的是该 CPP 的截图与文案，而非默认产品页。
- 修改 CPP 关键词不需要走审核，所以可以快速 A/B 不同关键词组合。

Offer Codes 这次扩展最大：从仅支持订阅，扩展到 consumables、non-consumables、non-renewing subscriptions。规则：

- 每个 IAP 最多 10 个活跃 offer
- 每 app 每季度最多 100 万个 offer code（订阅 + IAP 合计）
- 三档 eligibility：从未消费 / 30 天前消费过 / 近 30 天有消费
- Sandbox 环境也能生成和兑换 code，每 app 每季度 10000 个，单个 sandbox Apple Account 无兑换上限（[13:18](https://developer.apple.com/videos/play/wwdc2025/328/?time=798)）

兑换路径：deep link / QR code / 应用内输入。一旦用户兑换，App Store 自动安装 app，开发者只需用 StoreKit 识别 transaction 并发放权益。

**3. 告知用户你的 App 是否适合他们（Chinedu）**

三个新东西：Review Summaries（LLM 从评论生成摘要，开发者可在 ASC 报告问题）、年龄分级从 3 档扩展到 5 档（新增 messaging/chat、UGC、advertising 等声明项；可声明 app 内家长控制；支持手动调高，比如「我们政策要求 16 岁以上」）、Accessibility Nutrition Labels。

Accessibility Nutrition Labels 是全新功能：

- 在产品页展示 app 支持的无障碍特性（VoiceOver、Larger Text 等）
- **按设备独立声明**——同一个 app 在 iPhone 上支持 VoiceOver、在 Apple TV 上不支持，可以分别声明（[19:45](https://developer.apple.com/videos/play/wwdc2025/328/?time=1185)）
- 默认存为 draft，反复编辑后再发布；可绑定一个外部说明页 URL
- 发布后随时可以编辑

**4. 其他更新（Michael）**

App Analytics 新增 100+ 指标，订阅和变现数据全部展开；Game Center 改版，引入 Activities 和 Challenges；App Review 提交流程支持把 Apple-Hosted Background Assets、Game Center 类型作为独立项提交，也可以组合多项为 draft submission 一并送审（[24:02](https://developer.apple.com/videos/play/wwdc2025/328/?time=1442)）。

## 核心启发

- **立刻检查新年龄分级**：ASC 会用旧问卷答案自动算新分级，但新增了 messaging/chat、UGC、advertising 三类声明项，旧问卷里没有。**为什么值得做**：分级错位会直接影响下载和家长筛选；**怎么开始**：进 ASC → Age Ratings → 走一遍新问卷，重点填新增问题；如果你们公司政策要求高于计算结果，用 override 调高。

- **给每个 CPP 分配独特关键词**：CPP 关键词可以让搜索结果里展示对应 CPP 而非默认产品页，且改关键词不需要重新审核。**为什么值得做**：等于免费多了几个搜索入口；**怎么开始**：列出你 app 的 3-5 个高意图搜索词，把每个词分配给最匹配的 CPP，每种语言独立配置，上线后在 App Analytics 里看每个 CPP 的搜索流量。

- **Offer Codes 按消费状态分层**：新版 IAP offer codes 支持「从未消费 / 30 天未消费 / 近 30 天有消费」三档 eligibility。**为什么值得做**：同一张优惠券给所有人是浪费——拉新、唤醒、留存的合理价格点不一样；**怎么开始**：先在 sandbox 生成三套 code 跑通流程，然后给三类用户发不同力度的 offer，用 ASC 报告对比转化率。

- **Accessibility Nutrition Labels 先做 draft 再发布**：默认存为 draft 是为了防止误声明。**为什么值得做**：声明了不支持等于隐性承诺；**怎么开始**：让 QA 按 Apple 的 detailed guidance 逐项实测每台设备上的支持情况，分设备独立声明，确认无误后再发布。

- **把 Review Summary 当成产品反馈**：LLM 生成的 summary 高度浓缩了用户关注点。**为什么值得做**：比手动逐条读评论高效；**怎么开始**：每周扫一次 ASC 里的 Review Summary，把反复出现的关键词导入产品 backlog；如果 summary 提取得不准，用 ASC 的 report concern 反馈。
