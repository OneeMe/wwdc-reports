## Highlight

> 以前测 App Intents，要么写极度脆弱的 UI 测试去点 Shortcuts 界面，要么在代码里直接调 `perform()` 绕过系统的参数解析和 Entity 匹配。`AppIntentsTesting` 框架让你通过 Bundle ID 跨进程调用真实的 App Intents 栈，像写单元测试一样构造 Intent、传入参数、执行并断言返回值——走的是和用户一模一样的系统底层代码路径。

---

## 核心内容

### 1. 这场演讲解决什么问题

App Intents 是 Siri、Shortcuts、Spotlight、Widgets 的系统级基础设施。但测试它一直是个痛点：

- UI 测试脆弱：Shortcuts 界面一变，测试就挂。
- 直接调 `perform()`：绕过了系统的参数解析、Entity 匹配和权限检查，测了个寂寞。
- 没有自动化：靠手动在 Shortcuts App 里点点点，无法集成到 CI。

`AppIntentsTesting` 框架解决了这些问题。它寄生在 XCUITest 里，但通过 Bundle ID 跨进程调用真实的 App Intents 栈——没有 Mock，没有 Stub，走的是 Siri 和 Shortcuts 实际使用的同一条代码路径。

### 2. 第一个测试：执行一个 Intent

创建一个 UI Testing Bundle（注意：测试 Runner 和 App 需要用同一个 Development Team 签名）。

```swift
import AppIntentsTesting

func testCreateCalendar() async throws {
    let definitions = IntentDefinitions(bundleIdentifier: "com.example.apple-samplecode.CometCal")
    let createCalendar = definitions.intents["CreateCalendarIntent"]
    let result = try await createCalendar.makeIntent(
        name: "Occupy Saturn",
        color: "red"
    ).run()
    XCTAssertEqual(try result.value.title, "Occupy Saturn")
}
```

关键点：

- `IntentDefinitions` 通过 Bundle ID 获取 App 中定义的所有 Intent、Entity 和 Query，不需要 import App 的代码。
- `intents["IntentName"]` 通过字符串下标获取 Intent 定义，没有自动补全，需要确保名字拼写正确。
- `makeIntent()` 传入参数名和值，框架会自动做类型转换（包括 `AppEnum` 的 raw string 到类型的转换）。
- `.run()` 执行 Intent，返回结果可以断言。

### 3. 测试 Entity String Query

Entity Query 是 App Intents 的核心——Siri 和 Spotlight 通过它找到你的内容。测试它确保搜索逻辑正确：

```swift
func testEventStringQuery() async throws {
    let results = try await eventEntityDefinition
        .entities(matching: "Cosmic Ray")

    XCTAssertEqual(results.count, 1)
    XCTAssertEqual(try results[0].title, "Cosmic Ray Calibration")
}
```

对应的 Query 实现：

```swift
struct EventEntityQuery: EntityStringQuery {
    func entities(for identifiers: [EventEntity.ID]) async throws -> [EventEntity] {
        // 通过 ID 获取实体
    }

    func suggestedEntities() async throws -> [EventEntity] {
        // 返回建议实体
    }

    func entities(matching string: String) async throws -> [EventEntity] {
        try calendarManager.fetchEvents()
            .filter { $0.title.localizedCaseInsensitiveContains(string) }
            .map(\.entity)
    }
}
```

关键点：

- 测试框架会调用你的 `entities(matching:)` 方法，传入搜索字符串。
- 这是真正的模糊匹配测试，确保 Siri 说"找 Cosmic Ray 那个活动"时能正确命中。
- 建议先写 Query 的测试，再实现 Query 逻辑（TDD）。

### 4. 链式 Intent 测试

真实场景中，用户经常连续执行多个操作。测试框架支持在一个测试里链式调用：

```swift
func testCreateAndUpdateEvent() async throws {
    let createResult = try await createEventDefinition.makeIntent(
        title: "Asteroid Dodgeball Practice",
        startDate: Date(),
        isAllDay: false,
        calendar: "Deep Space"
    ).run()

    XCTAssertEqual(try createResult.value.title, "Asteroid Dodgeball Practice")

    let updateResult = try await updateEventDefinition.makeIntent(
        title: "Asteroid Dodgeball Rules Overview",
        event: createResult.value
    ).run()

    XCTAssertEqual(try updateResult.value.title, "Asteroid Dodgeball Rules Overview")
}
```

关键点：

- 前一个 Intent 的结果可以直接作为后一个 Intent 的参数传入。
- 这模拟了真实用户的工作流：创建日历事件 → 修改事件标题。
- 链式测试能发现单个 Intent 测试发现不了的状态依赖问题。

### 5. 测试专用的 Intent（Seed Intent）

测试需要可控的初始数据。可以创建只在 DEBUG 模式下可用的 Seed Intent：

```swift
#if DEBUG
struct SeedSampleEventsIntent: AppIntent {
    static let isDiscoverable = false

    func perform() async throws -> some IntentResult {
        // 创建已知的测试数据
        return .result()
    }
}
#endif
```

关键点：

- `isDiscoverable = false` 确保这个 Intent 不会出现在 Shortcuts App 或 Siri 中。
- 用 `#if DEBUG` 包裹，发布版本中自动排除。
- 在 `setUp()` 中调用 Seed Intent，确保每个测试的初始状态一致。

### 6. 测试 Spotlight 索引

App Intents 的内容会自动进入 Spotlight 索引。测试框架可以验证索引是否正确：

```swift
func testNewEventIndexedInSpotlight() async throws {
    let before = try await eventEntityDefinition.spotlightQuery("Supernova Viewing Party")
    XCTAssertTrue(before.isEmpty, "Event should not exist in Spotlight yet")

    // ... 创建 "Supernova Viewing Party" 事件

    let after = try await eventEntityDefinition.spotlightQuery("Supernova Viewing Party")
    XCTAssertEqual(after.count, 1)
    XCTAssertEqual(try after[0].title, "Supernova Viewing Party")
}
```

### 7. 测试 View Annotations

View Annotations 让 Siri 知道屏幕上当前展示的是什么内容。测试框架可以验证标注是否正确：

```swift
func testEventViewAnnotation() async throws {
    try await openEventDefinition.makeIntent(target: "Morning Launch Briefing").run()

    // 确认正确的事件页面已打开
    let app = XCUIApplication()
    let title = app.staticTexts["Morning Launch Briefing"]
    XCTAssertTrue(title.waitForExistence(timeout: 5))

    let annotations = try await eventEntityDefinition.viewAnnotations()

    XCTAssertEqual(annotations.count, 1, "Expected exactly one view annotation")
    XCTAssertEqual(try annotations[0].entity.title, "Morning Launch Briefing")
}
```

关键点：

- 这里混合了 UI 测试（验证页面正确打开）和 Intent 测试（验证 View Annotation）。
- View Annotation 测试确保 Siri 说"把这张照片发给 Kevin"时，知道"这张照片"指的是哪一张。

## 最佳实践

- **已有项目迁移**：立刻把 CI 里那些靠点击 Shortcuts 界面来验证的 UI 测试删掉，换成 `AppIntentsTesting`。这能让你的测试运行时间缩短 80% 以上，且彻底告别"按钮位置变了导致测试挂了"的破事。

- **新项目采用**：强烈建议为测试专门编写 Seed Intent。把这些 Intent 用 `#if DEBUG` 包裹，并设置 `isDiscoverable = false`。在 `setUp()` 方法里一键清空数据库并注入固定测试数据，让每个测试用例都保持绝对的幂等性。

- **实战中容易踩的坑**：Entity 的解析失败是最常见的问题。当你在测试里传入一个字符串（比如日历名称 "Deep Space"），系统会在后台调用你的 `EntityQuery` 去匹配真实的 Entity。如果你的 Query 没写好，Intent 执行会直接报错。这也是为什么 Session 里强调要用 TDD 的方式，先写 `entities(matching:)` 的测试，再去实现 Query 逻辑。

- **测试运行要求**：AppIntentsTesting 需要测试 Runner 和 App 使用同一个 Development Team 签名。创建 UI Testing Bundle 时务必选对 Team，否则测试会报签名错误。
