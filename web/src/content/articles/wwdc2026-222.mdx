## Highlight

> MetricKit 在 iOS 27 被用纯 Swift 完全重写，抛弃了老旧的 Delegate 模式，全面拥抱 AsyncSequence。最大的杀器是 StateReporting 框架：它允许你把 App 的运行状态（当前在哪个 Tab、处于什么用户流）作为维度，和性能指标做交叉分析。现在你可以精准看到"用户在查看大尺寸列表且未排序时，内存峰值到底是多少"。

## 核心内容

### 1. 这场演讲解决什么问题

性能优化的标准流程是：收集数据 → 分析问题 → 定位根因 → 修复 → 监控结果。MetricKit 负责的是"收集数据"这一步。

但老版 MetricKit 有几个痛点：

- API 是 Objective-C 时代的，用起来很别扭
- 拿到的是 App 整体数据，不知道问题出在哪个页面
- Delegate 回调容易漏数据

iOS 27 的 MetricKit 全部解决了这些问题。

### 2. 全新 Swift-first API：AsyncSequence

新的 `MetricManager` 用 AsyncSequence 提供数据流：

```swift
import MetricKit

let manager = MetricManager()

// 接收性能指标
for await report in manager.metricReports {
    processReport(report)
}

// 接收诊断数据
for await report in manager.diagnosticReports {
    processReport(report)
}
```

关键点：
- 在 App 启动时就开始监听，避免延迟订阅导致数据丢失
- `MetricManager` 需要保持存活，让数据流持续接收
- 建议在 detached task 或专门的服务类中执行

### 3. Metrics：App 的健康信号

Metrics 告诉你性能趋势是变好还是变差：

- **响应性指标**：启动时间、Hang 时间、动画性能
- **资源消耗指标**：CPU、GPU、磁盘写入、网络传输
- **新增指标**：Metal 帧率（游戏开发者重点关注）

数据按 metric group 组织：`.cpu`、`.memory`、`.display`、`.gpu` 等。

```swift
for await report in manager.metricReports {
    let intervalEntries = report.intervalEntries
    let fullDayEntry = intervalEntries.fullDayEntry

    for entry in intervalEntries {
        let memoryMetrics = entry.values.filter { $0.metricGroup == .memory }
        for metric in memoryMetrics {
            switch metric {
            case .peakMemory(let peak):
                processPeakMemory(peak)
            default: break
            }
        }
    }
}
```

### 4. Diagnostics：定位具体问题

Diagnostics 告诉你哪段代码导致了性能问题：

- **Crash**：调用栈、终止原因、终止类别
- **Hang**：卡顿的调用栈
- **新增**：Memory Exception（内存超限导致的终止）

```swift
for await report in manager.diagnosticReports {
    switch report.result {
    case .crash(let crash):
        let backtrace = crash.callStackTree
        let reason = crash.terminationReason
        let category = crash.terminationCategory
        processCrash(backtrace: backtrace, reason: reason, category: category)
    case .hang(let hang):
        processHangDiagnostic(hang)
    default: break
    }
}
```

### 5. StateReporting：把性能和状态关联起来

这是今年最大的升级。以前你只能看到"App 平均 Hang 了 3 秒"，现在你能看到"用户在 Tab 1 时 Hang 了 1 秒，在 Tab 2 时 Hang 了 2 秒"。

**定义状态域**：

```swift
import MetricKit
import StateReporting

let domain = StateReportingDomain("com.myapp.tabs")
let manager = MetricManager(enabledStateReportingDomains: [domain])
```

**上报状态转换**：

```swift
let reporter = StateReporter.reporter(for: domain.rawValue)
reporter.reportTransition(to: "Reports")
```

**带结构化元数据的状态**：

```swift
@ReportableMetadata
struct ViewConfiguration {
    let listSize: String
    let isSorted: Bool
}

let reporter = StateReporter.reporter(
    for: domain.rawValue,
    stableMetadata: ViewConfiguration.self
)

reporter.reportTransition(
    to: "Reports",
    stableMetadata: ViewConfiguration(listSize: "large", isSorted: false)
)
```

**按状态维度编码上报数据**：

```swift
for await report in manager.metricReports {
    let encoder = JSONEncoder()
    let formatKey = MetricReport.encodingFormatKey
    encoder.userInfo[formatKey] = MetricReport.EncodingFormat.byStateReportingDomain
    let jsonData = try encoder.encode(report)
    sendToServer(jsonData)
}
```

关键点：
- `@ReportableMetadata` 宏自动生成 Codable 支持
- `stableMetadata` 描述状态的静态属性（如列表大小、是否排序）
- 服务器可以按状态和元数据维度做交叉分析

## 最佳实践

- **老项目迁移**：不要想着一步到位。先把 `MXMetricManager` 替换为新的 `MetricManager`，跑通 AsyncSequence 的数据上报链路。确认服务端能正确解析新的 Codable 结构后，再逐步引入 StateReporting
- **新项目建议**：强烈建议第一天就把 StateReporting 规划进架构里。把 App 的核心 Tab、关键用户流（如"结账流程"、"视频播放"）定义为独立的 State。不要在每个 ViewController 的 `viewDidAppear` 里无脑上报 State，这会导致状态碎片化，让交叉分析失去意义
- **实战避坑**：State 的生命周期管理是关键。如果用户切到后台，你的 State 没有正确 reset 或者 pause，MetricKit 会把后台挂起的时间也算进这个 State 的 Hang 或 CPU 指标里，导致数据严重失真
