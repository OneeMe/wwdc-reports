## Highlight

> Metal 原生用 Objective-C 设计。如果你的代码库是 C++，需要一层桥接才能使用 Metal。metal-cpp 就是这层桥接——一个 header-only 库，提供 100% 的 Metal API 覆盖率，每个 C++ 调用直接映射到对应的 Objective-C 方法。关键难点是对象生命周期管理：metal-cpp 使用手动引用计数（MRR），而 Objective-C 使用 ARC。Xcode 14 提供了 NS::SharedPtr 和 autorelease pool 的 C++ 封装来简化内存管理。

## 核心内容

### metal-cpp 的定位与价值

Metal 是 Apple 平台的原生图形和计算 API，但它完全基于 Objective-C 设计。对于 C++ 游戏引擎或应用来说，这层语言壁垒意味着要么把整个项目迁移到 Objective-C（不现实），要么手写桥接代码（维护成本高）。

metal-cpp 是 Apple 官方提供的解决方案：一个 header-only 库，提供 100% 的 Metal API 覆盖率。它的核心设计原则是「直接映射」——每个 C++ 调用都直接翻译成对应的 Objective-C 方法调用，没有中间层、没有封装抽象，调用开销几乎为零。

一个对比能说明问题。用 Objective-C 绘制三角形的代码：

```objc
id<MTLCommandBuffer> cmd = [_commandQueue commandBuffer];
id<MTLRenderCommandEncoder> enc = [cmd renderCommandEncoderWithDescriptor:pRpd];
[enc setRenderPipelineState:_pPSO];
[enc drawPrimitives:MTLPrimitiveTypeTriangle vertexStart:0 vertexCount:3];
[enc endEncoding];
[cmd presentDrawable:view.currentDrawable];
[cmd commit];
```

用 metal-cpp 的 C++ 版本：

```cpp
MTL::CommandBuffer* pCmd = _pCommandQueue->commandBuffer();
MTL::RenderCommandEncoder* pEnc = pCmd->renderCommandEncoder(pRpd);
pEnc->setRenderPipelineState(_pPSO);
pEnc->drawPrimitives(MTL::PrimitiveTypeTriangle, NS::UInteger(0), NS::UInteger(3));
pEnc->endEncoding();
pCmd->presentDrawable(pView->currentDrawable());
pCmd->commit();
```

API 命名和调用顺序完全一致，只是从方括号语法变成了箭头操作符。这种一致性让 Objective-C 文档和示例代码可以直接对照理解，学习成本极低。

### 对象生命周期管理的根本差异

metal-cpp 的真正难点不在 API 调用，而在内存管理。Objective-C 使用 ARC（自动引用计数），编译器自动插入 retain/release 操作；而 metal-cpp 使用 MRR（手动引用计数），需要开发者手动管理。

Cocoa 的命名约定决定了所有权：以 `alloc`、`new`、`copy`、`mutableCopy`、`create` 开头的方法返回的对象，调用者拥有所有权，必须负责 release。其他方法返回的对象，调用者不拥有所有权，不应该 release。

这条规则在 metal-cpp 中同样适用。看一个例子：

```cpp
MTL::Device* pDevice = MTL::CreateSystemDefaultDevice(); // 'Create' 开头，你拥有它
// ... 使用 pDevice ...
pDevice->release(); // 必须手动释放

MTL::CommandBuffer* pCmd = _pCommandQueue->commandBuffer(); // 非 'Create' 开头，你不拥有它
// ... 使用 pCmd ...
// 不应该调用 pCmd->release()
```

违反规则会导致内存泄漏（该释放的不释放）或崩溃（不该释放的释放了）。

### Xcode 14 的工具支持

Apple 在 Xcode 14 中提供了三个工具来简化 metal-cpp 的内存管理。

**NS::SharedPtr 智能指针**：类似 C++11 的 `std::shared_ptr`，自动管理引用计数。构造时自动 retain，析构时自动 release。适合长期持有的对象。

```cpp
NS::SharedPtr<MTL::Device> pDevice = MTL::CreateSystemDefaultDevice();
// 使用 pDevice ...
// 离开作用域时自动 release
```

**NS::TransferPtr 所有权转移**：用于转移所有权，类似 `std::unique_ptr`。接收者接管对象的生命周期。

```cpp
{
    auto ptr = NS::TransferPtr(pMRR); // pMRR 的所有权转移给 ptr
    // 使用 ptr ...
}
// 离开作用域时，ptr 自动释放 pMRR
```

**NS::AutoreleasePool 自动释放池**：C++ 版本的 autorelease pool。池被销毁时，池中所有对象都会收到 release 消息。适合短期大量创建对象的场景，避免峰值内存占用。

```cpp
NS::AutoreleasePool* pPool = NS::AutoreleasePool::alloc()->init();
MTL::CommandBuffer* pCmd = _pCommandQueue->commandBuffer();
MTL::RenderPassDescriptor* pRpd = pView->currentRenderPassDescriptor();
MTL::RenderCommandEncoder* pEnc = pCmd->renderCommandEncoder(pRpd);
pEnc->endEncoding();
pCmd->presentDrawable(pView->currentDrawable());
pCmd->commit();
pPool->release(); // 释放池，池中所有对象也会被释放
```

### 混合语言架构的适配模式

在实际项目中，C++ 游戏引擎往往需要调用 Objective-C 的系统 API（如 MTKView），而 Objective-C UI 代码也需要调用 C++ 的渲染逻辑。Apple 推荐的方案是适配器模式。

**从 Objective-C 调用 C++**：创建一个 Objective-C 类，持有 C++ 对象的指针，方法内部调用 C++ 对象的方法。

```objc
@interface AAPLRendererAdapter ()
{
    AAPLRenderer* _pRenderer;
}
@end

@implementation AAPLRendererAdapter
- (void)drawInMTKView:(MTKView *)pMtkView
{
    _pRenderer->draw((__bridge MTK::View*)pMtkView);
}
@end
```

**从 C++ 调用 Objective-C**：创建一个 C++ 类，内部持有 Objective-C 对象的指针（用 `__bridge` 转换），方法内部调用 Objective-C 方法。

```cpp
CA::MetalDrawable* AAPLViewAdapter::currentDrawable() const
{
    return (__bridge CA::MetalDrawable*)[(__bridge MTKView *)m_pMTKView currentDrawable];
}

MTL::Texture* AAPLViewAdapter::depthStencilTexture() const
{
    return (__bridge MTL::Texture*)[(__bridge MTKView *)m_pMTKView depthStencilTexture];
}
```

**跨边界所有权转移**：当对象在 Objective-C 和 C++ 之间传递时，需要明确所有权的转移。`__bridge_retained` 表示 C++ 接管所有权（C++ 负责 release），`__bridge` 表示不转移所有权（Objective-C 仍负责 release）。

```cpp
MTL::Texture* newTextureFromCatalog(MTL::Device* pDevice, const char* name,
                                    MTL::StorageMode storageMode, MTL::TextureUsage usage)
{
    NSDictionary<MTKTextureLoaderOption, id>* options = @{
        MTKTextureLoaderOptionTextureStorageMode : @((MTLStorageMode)storageMode),
        MTKTextureLoaderOptionTextureUsage : @((MTLTextureUsage)usage)
    };

    MTKTextureLoader* textureLoader = [[MTKTextureLoader alloc]
                                        initWithDevice:(__bridge id<MTLDevice>)pDevice];

    NSError* __autoreleasing err = nil;
    id<MTLTexture> texture = [textureLoader
                        newTextureWithName:[NSString stringWithUTF8String:name]
                               scaleFactor:1
                                     bundle:nil
                                    options:options
                                      error:&err];

    return (__bridge_retained MTL::Texture*)texture; // C++ 接管所有权
}
```

## 最佳实践

### 项目配置

- **宏定义唯一性**：在唯一一个 .cpp 文件中定义 `NS_PRIVATE_IMPLEMENTATION`、`CA_PRIVATE_IMPLEMENTATION`、`MTL_PRIVATE_IMPLEMENTATION`，避免重复定义错误。
- **C++ 标准版本**：项目需要设置 C++17 或更高版本的方言，metal-cpp 依赖 C++17 的部分特性。
- **框架链接**：在 Xcode 中添加 Foundation、QuartzCore 和 Metal 三个框架。

### 内存管理

- **优先使用智能指针**：长期持有的对象用 `NS::SharedPtr` 管理生命周期，减少手动 retain/release 的出错概率。
- **明确所有权规则**：遵循 Cocoa 命名约定，`Create` 开头的方法返回的对象必须手动释放，其他方法返回的对象不应该释放。
- **避免混合 new/delete**：不要对 metal-cpp 对象使用 C++ 的 `new`/`delete`，统一使用 metal-cpp 的 `alloc()`/`release()`。

### 架构设计

- **适配器模式分离语言边界**：在 Objective-C 和 C++ 交界处创建适配器类，把跨语言调用集中在一处，降低维护成本。
- **明确所有权转移**：对象跨语言传递时，用 `__bridge_retained` 或 `__bridge` 明确所有权，避免重复释放或泄漏。
- **利用 autorelease pool**：短期大量创建对象的场景（如每帧渲染），用 `NS::AutoreleasePool` 避免峰值内存占用。

## 核心启发

### 从 Objective-C 文档直接迁移

metal-cpp 的 API 设计严格遵循 Objective-C 原版，这意味着所有 Objective-C 的 Metal 文档、示例代码、Stack Overflow 答案都可以直接对照理解。遇到不知道如何调用的 API，直接看 Objective-C 版本的文档，把方括号语法换成箭头操作符即可。

### 内存管理是第一道坎

metal-cpp 的学习曲线主要在内存管理。手动引用计数在 C++ 中显得繁琐，但这是 Objective-C 历史遗留的设计。熟练掌握 Cocoa 命名约定，优先使用智能指针，可以大幅降低出错概率。

### 适配器模式值得投入

如果项目中有大量 Objective-C 和 C++ 互操作，花时间设计清晰的适配器类是值得的。把跨语言调用集中在一处，一方面降低维护成本，另一方面未来迁移到纯 C++ 或纯 Objective-C 也更容易。
