## Highlight

> Containerization 是 Apple 开源的 Swift 框架，每个 Linux 容器跑在自己的轻量级 VM 里，亚秒级启动，独立 IP，无容器运行时资源开销为零。

## 核心内容

在 Mac 上跑 Linux 容器，过去只有一条主流路径：启动一个大 VM，把所有容器塞进去共用。资源在内部分配，目录共享要先挂到 VM 再透到容器，端口要做映射，攻击面也跟着大 VM 一起被放大。开发者得到的是 Linux 环境，但安全和隔离都在打折。

Apple 在 WWDC25 给出了另一个方向：Containerization。这是一个用 Swift 写的开源框架，提供镜像管理、容器执行和一个 Swift 实现的 init 系统。最关键的取舍是：每个容器跑在自己的轻量级 VM 里，启动时间在亚秒级。每个容器拿到独立 IP，不用端口映射；目录按容器粒度共享，只有发起请求的容器能看到内容；没有容器在跑时，资源开销为零。框架之上还提供了一个开源 CLI 工具 `container`，几百毫秒就能进入 Alpine 容器的 shell（[11:03](https://developer.apple.com/videos/play/wwdc2025/346/?time=663)）。

## 详细内容

镜像管理部分（[04:10](https://developer.apple.com/videos/play/wwdc2025/346/?time=250)）。镜像是文件系统内容加默认配置的分发产物，作为新容器的模板。Containerization 提供 API 从 Registry 拉取，把响应写到本地。镜像的文件系统并非按文件解包，而被格式化成一块 block device：创建一个大文件，再用 EXT4 格式化。EXT4 是 Linux 广泛使用的文件系统，框架提供了 Swift 包，可以直接从 Swift 端格式化、创建目录结构、填充 EXT4 内容（[05:41](https://developer.apple.com/videos/play/wwdc2025/346/?time=341)）。

虚拟机内部由 `vminitd` 接管（[07:14](https://developer.apple.com/videos/play/wwdc2025/346/?time=434)）。它是 Swift 写的 init 系统，作为 VM 的第一个进程，负责给网络接口分配 IP、挂载镜像 block device 暴露的文件系统、启动并监管 VM 内所有进程，并向主机暴露 API 用于远程拉起进程。Containerization 提供的最小文件系统里没有 libc、没有动态库、也没有 cd/cp/ls 这类 core utilities（[08:22](https://developer.apple.com/videos/play/wwdc2025/346/?time=502)）。为了让 `vminitd` 能在这种环境里跑，它用 Swift Static Linux SDK 交叉编译成静态可执行文件，链接 musl 这个对静态链接支持良好的 libc 实现（[08:43](https://developer.apple.com/videos/play/wwdc2025/346/?time=523)）。

`container` CLI 把上面这些拼成开发者可用的入口（[09:26](https://developer.apple.com/videos/play/wwdc2025/346/?time=566)）。它由 CLI 和若干 XPC 服务组成，分别负责 Storage、镜像管理、Network（IP 分配与 DNS）以及容器运行时。拉镜像：

```sh
container image pull alpine:latest
```

关键点：
- `container` 是基于 Containerization 框架构建的开源 CLI 工具
- `image pull` 子命令向 Registry 请求 Alpine 最新版的文件系统和配置
- 拉取过程会在本地创建 block 文件，存放 EXT4 格式化后的镜像内容

跑一个交互式 shell（[10:43](https://developer.apple.com/videos/play/wwdc2025/346/?time=643)）：

```sh
container run -t -i alpine:latest sh
```

关键点：
- `run` 会用镜像的文件系统和配置创建容器，并通过框架启动一台轻量 VM
- `-t` 申请 TTY 终端设备，`-i` 把当前输入接入容器，配合即得到交互式 shell
- 最后两段是镜像名和要执行的命令，这里直接跑 `sh`
- 演示中容器在几百毫秒内进入 shell，`uname -a` 显示 Linux 环境，`ps aux` 只能看到自身的 shell 和 ps 进程，主机和其他容器进程不可见（[11:08](https://developer.apple.com/videos/play/wwdc2025/346/?time=668)）

整套设计的安全收益来自两点叠加：每个容器的隔离边界等同于完整 VM；VM 内部因为没有 core utilities 和动态库，攻击者落地后能用的工具极少。

## 核心启发

- **本地开发先用 `container` CLI 替代 Docker Desktop 跑通**：为什么值得做——免去大 VM 的资源常驻开销，没容器跑时不占内存；独立 IP 让多服务调试不用再写一堆端口映射。怎么开始——`container image pull` 拉常用基础镜像，把团队 Dockerfile 在本地走一遍 `container run`，确认行为一致。
- **用 Swift Static Linux SDK 产出零依赖 Linux 二进制**：为什么值得做——`vminitd` 证明了可以用 Swift 交叉编译出无 libc 依赖的静态 Linux 可执行文件，部署到任意最小镜像不用担心动态库问题。怎么开始——在 Mac 上配置 Static Linux SDK，挑一个原本用 Go/Rust 写的小工具用 Swift 重写，链接 musl，验证体积和启动速度。
- **把 EXT4 Swift 包用在镜像/磁盘工具链里**：为什么值得做——以前从 macOS 端构造 Linux 文件系统得借助 `e2fsprogs` 或 Docker，现在可以纯 Swift 完成格式化、建目录、填内容。怎么开始——参考 Containerization 仓库里的 EXT4 包，写一个把本地目录打包成 EXT4 block file 的 CLI，用作 VM 的根盘。
- **用每容器独立 IP 重构本地多服务调试**：为什么值得做——独立 IP 等于把生产环境的 service-to-service 调用模式直接搬到本地，少一层 NAT 心智负担。怎么开始——把项目里多个相互调用的服务各跑在一个容器，用容器 IP 直连替代 `localhost:portN`，顺手把 `.env` 里的端口映射清掉。
