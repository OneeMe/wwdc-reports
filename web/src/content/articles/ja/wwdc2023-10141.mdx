## ハイライト

> Apple は、WWDC23 で Get Transaction Info エンドポイントを App Store サーバー API に追加し、サブスクリプション ステータス フィールドとonlyFailures フィルターを Notifications V2 に追加し、verifyReceipt と Notices V1 を正式に放棄して、開発者がより最新の JWS 署名データ システムに移行することを促進しました。

## 主な内容

### 単一トランザクションを直接クエリするには、transactionId を使用します。

以前は、サーバー上のトランザクションを検証するには、Get Transaction History を呼び出してから、結果の複数ページを調べて一致するレコードを見つける必要がありました。ユーザーの取引履歴が長い場合、このプロセスは遅くて面倒です。さらに厄介なことに、完了した消費トランザクションはトランザクション履歴の取得の応答に表示されず、消費トランザクションを検証することができなくなります。

([03:12](https://developer.apple.com/videos/play/wwdc2023/10141/?time=192)) Apple は、新しい Get Transaction Info エンドポイントを導入しました。トランザクションの署名情報を直接取得するには、transactionId を指定するだけです。完了した消費トランザクションを含む、すべてのタイプのトランザクション ID がサポートされます。

呼び出し方法は非常に簡単です。

```
GET https://api.storekit.itunes.apple.com/inApps/v1/transactions/{transactionId}
```

応答には `signedTransactionInfo` フィールドが含まれており、これをデコードしてトランザクションの完全な情報を表示できます。

([06:32](https://developer.apple.com/videos/play/wwdc2023/10141/?time=392)) もう 1 つの便利な更新: 以前はパス パラメーターとして `originalTransactionId` を必要としたコア エンドポイント (トランザクション履歴の取得、すべてのサブスクリプション ステータスの取得など) が、任意の `transactionId` の使用をサポートするようになりました。最初に ID を変換するために Get Transaction Info を使用する必要はなくなり、直接呼び出すことができます。

### 購読状況が一目瞭然

([07:42](https://developer.apple.com/videos/play/wwdc2023/10141/?time=462)) サブスクリプション ステータスの追跡は、サブスクリプション ベースのアプリケーションの中核的な要件です。通知 V2 は、サブスクリプションのステータスが変化するとイベントを送信しますが、一部の通知タイプは現在のステータスを直接伝えることができません。

たとえば、返金通知を受け取った場合、サブスクリプションが取り消されたかどうかを直接判断することはできません。ユーザーが同じoriginalTransactionIdで新しい更新トランザクションを実行している場合、サブスクリプションのステータスは依然としてアクティブである可能性があります。届出データだけでは正しい判断をすることはできません。

([10:22](https://developer.apple.com/videos/play/wwdc2023/10141/?time=622)) Apple は、Notifications V2 のデータ オブジェクトに新しい `status` フィールドを追加しました。これは、サブスクリプションの 5 つのコア状態の 1 つを直接表す整数です。自動更新サブスクリプションに関連するすべての通知にはこのフィールドが含まれるため、サーバーはステータスを確認するために追加の API 呼び出しを行う必要がなくなりました。

### 失敗通知のみを取得する

([11:36](https://developer.apple.com/videos/play/wwdc2023/10141/?time=696)) サーバーに障害が発生すると、App Store が正常に通知を送信できない場合があります。通知履歴の取得エンドポイントを使用すると、過去 6 か月間の V2 通知をリクエストでき、これを使用して見逃した通知を回復できます。

ただし、問題は、サーバーが正常に実行されている場合でも、一時的なネットワークの問題により、個々の通知を見逃す場合があるということです。この場合、クエリを実行するための明確な時間枠がなく、受信した多数の通知を調べて欠落を見つけることしかできません。

([12:30](https://developer.apple.com/videos/play/wwdc2023/10141/?time=750)) Apple は、通知履歴の取得に新しい `onlyFailures` リクエスト フィールドを追加しました。有効にすると、応答には、再試行中の通知など、サーバーに正常に配信されなかった通知のみが含まれます。

リクエスト例:

```json
{
  "onlyFailures": true
}
```

応答内の各通知エントリには、各送信試行の結果を記録する `sendAttempts` 配列が含まれます。後続の再試行が成功すると、通知は `onlyFailures` のクエリ結果に表示されなくなります。

### verifyReceipt は正式に廃止されました

([14:44](https://developer.apple.com/videos/play/wwdc2023/10141/?time=884)) Apple は、verifyReceipt エンドポイントと App Store Server Notices V1 が正式に非推奨になったことを発表しました。これら 2 つの API は、新機能の更新を受信しなくなります。

App Store サーバー API への移行には、次の 3 つの手順が必要です。

1. アプリの ID を表す JWT を生成します
2. 各ユーザーのtransactionIdを保存します。
3.transactionIdを使用してコアエンドポイントを呼び出します。

通知 V2 への移行は簡単です。

1. V2 形式を解析するためにサーバーを準備します (サーバー API と同じ JWS トランザクション形式を使用)
2. App Store Connect で通知設定を V1 から V2 に切り替える
3. 最初にサンドボックス環境で V2 通知をテストします

([19:35](https://developer.apple.com/videos/play/wwdc2023/10141/?time=1175)) Apple は、Swift、Java、Node.js、Python をサポートするオープン ソース ライブラリである App Store サーバー ライブラリもリリースしました。これにより、開発者はより簡単に API を呼び出し、署名データを検証し、レシートからトランザクション ID を抽出して移行を簡素化できます。

### トランザクション情報の取得エンドポイントの詳細

([05:47](https://developer.apple.com/videos/play/wwdc2023/10141/?time=347)) 新しい Get Transaction Info エンドポイントは、個々のトランザクションのサーバー側検証の問題点を解決します。

**リクエスト形式:**

```
GET /inApps/v1/transactions/{transactionId}
Authorization: Bearer {JWT}
```

**応答形式:**

```json
{
  "signedTransactionInfo": "eyJhbGciOiJFUzI1Ni..."
}
```

キーポイント:
- `signedTransactionInfo` は、JWS 形式の署名済みトランザクション データです。
- デコード後、productId、purchaseDate、type などを含む完全なトランザクション情報を取得できます。
- すべてのトランザクション タイプをサポートします: 消耗型、非消耗型、自動更新サブスクリプション、非更新型サブスクリプション
- 完了および未完了のトランザクションをサポート

### 通知 V2 のステータス フィールド

([10:30](https://developer.apple.com/videos/play/wwdc2023/10141/?time=630)) ステータス フィールドは整数で、次の 5 つのサブスクリプション ステータスに対応します。

|値 |ステータス |意味 |
|---|---|---|
| 1 |アクティブ |購読は有効です |
| 2 |期限切れ |サブスクリプションの有効期限が切れました |
| 3 |請求の再試行 |請求を再試行しています |
| 4 |請求猶予期間 |請求猶予期間 |
| 5 |取り消し済み |サブスクリプションが取り消されました |

このフィールドは、サブスクリプションの自動更新に関連するすべての通知に表示されます。返金通知を受け取った場合は、`status` を直接チェックして、コンテンツ アクセスを無効にする必要があるかどうかを確認してください。

###onlyFailures の使用シナリオ

([13:08](https://developer.apple.com/videos/play/wwdc2023/10141/?time=788))`onlyFailures` フィールドは 2 つのシナリオを解決します。

1. **既知のサーバー障害**: サーバーがダウンした後に回復し、障害中に失われた通知をクエリします。
2. **不明なネットワークの問題**: 日々の操作中に個別の通知が失われることがあります。欠落しているアイテムをすぐに見つけます。

```json
{
  "startDate": 1686000000000,
  "endDate": 1686086400000,
  "onlyFailures": true
}
```

応答内の `notificationHistory` 配列には、失敗した通知のみが含まれます。各エントリには次の内容が含まれます。
- `signedPayload`: 元の通知の署名内容
- `sendAttempts`: 送信試行レコード、最大 6 (初回送信 1 回 + 再試行 5 回)

### 移行パス

([17:16](https://developer.apple.com/videos/play/wwdc2023/10141/?time=1036)) verifyReceipt から移行:

古いプロセス:```
设备 → 收据 → 你的服务器 → verifyReceipt → Apple → 解码后的收据 → 你的服务器
```

新しいプロセス:```
设备 → transactionId → 你的服务器 → App Store Server API → 签名交易数据
```

Base64 でエンコードされたレシートを保存する必要はなくなり、transactionId だけを保存するだけになります。

## 重要なポイント

1. **リアルタイムのサブスクリプション ステータス ダッシュボードを構築します**
   - **やること**: カスタマー サービス チームがユーザーのサブスクリプション ステータスを確認できるように、サーバー上でリアルタイムのサブスクリプション ステータス ダッシュボードを維持します。
   - **䡡値**: 通知 V2 の `status` フィールドにより、ステータスの同期が直接的かつ信頼性の高いものになり、複雑な推論ロジックは必要なくなりました。
   - **開始側**: 通知 V2 受信エンドポイントを設定し、各通知の `status` フィールドを解析し、データベース内のユーザー サブスクリプション ステータスを更新します。

2. **インテリジェントな通知回復メカニズムの実装**
   - **やること**: `onlyFailures` クエリをサーバーの健全性チェック プロセスに統合して、見逃した通知を自動的に復元します
   - **䡡値**: ネットワークの問題は避けられないため、`onlyFailures` は回復不能通知を「履歴の確認」から「正確な測位」に変更します。
   - **開始側**: サーバーの起動中またはスケジュールされたタスク中に Get notification History を呼び出し、`onlyFailures: true` を渡して、返された欠落通知を処理します

3. **サーバー側のトランザクション検証の簡素化**
   - **やること**: 単一トランザクションの検証には、トランザクション履歴の取得ではなくトランザクション情報の取得を使用します。
   - **䡡値**: コードがシンプルになり、応答が速くなり、消費トランザクションの検証がサポートされます。
   - **Hajime**: 既存の検証ロジックを「クエリ履歴 + 検索一致」から、トランザクション ID を渡して Get Transaction Info を直接呼び出すように変更します。

4. **verifyReceipt の移行の計画**
   - **やること**: verifyReceipt から App Store Server API への移行計画を立てる
   - **䡡Value**: verifyReceipt は非推奨となり、新しい関数は JWS 署名データ システムでのみリリースされます。
   - **開始側**: App Store サーバー ライブラリのオープン ソース ライブラリを使用してレシートからtransactionIdを抽出し、verifyReceipt呼び出しを段階的に置き換えます。
