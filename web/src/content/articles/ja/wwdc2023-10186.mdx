## ハイライト

> Core Data は、iOS 17 で構造化データを整理するための複合属性、複雑なモデル変更を処理するための段階的移行、および起動時の長い待機を回避するための遅延移行を導入しました。

## 主な内容

アプリが反復されるにつれて、データ モデルはますます複雑になります。過去にこれらの問題に遭遇したとき、開発者は多くの場合、「大量の移行コードを記述する」か「Core Data を諦めて他のソリューションに切り替える」かの選択を迫られていました。

複合属性は、構造化データのストレージの問題を解決します。以前は、関連するプロパティのセットを複数の独立したフィールドにフラット化するか、Transformable 型を使用して独自のシリアル化コードを記述する必要がありました。複合属性を使用すると、一連の関連属性を複合属性にカプセル化し、辞書のようにアクセスして、キーパスをクエリ条件として直接使用できます。

段階的移行は、複雑なモデル変更による移行の問題を解決します。一部の変更 (エンティティの属性を個別のエンティティに分割するなど) は、軽量移行の機能を超えています。以前は、カスタム移行マッピングしか作成できませんでしたが、これはコード量が多く、エラーが発生しやすかったです。段階的移行を使用すると、複雑な変更を複数のステップに分割し、軽量の移行で処理できるようになり、Core Data がそれらのステップを順番に自動的に実行します。

遅延移行は、移行をブロックする UI の問題を解決します。一部の軽量の移行は自動的に完了できますが、古いデータのクリーンアップには時間がかかります。以前は、これはアプリの起動時に停止していました。遅延移行を使用すると、クリーニング作業をバックグラウンドに遅らせることができます。アプリは最初に新しいスキーマを使用し、データのクリーニングは後で行われます。

### Composite Attributes

([00:56](https://developer.apple.com/videos/play/wwdc2023/10186/?time=56)) 複合属性は、構造化データをカプセル化するための Core Data の新しい属性タイプです。

があると仮定します`Aircraft`エンティティ。以前はカラー スキームを保存するために Transformable タイプを使用していました。

```swift
@NSManaged public var colors: Data?  // Transformable，需要自定义 transformer
```

複合属性が利用できるようになりました。

```swift
@NSManaged public var colorScheme: [String: Any]?
```

Xcode モデル エディターで複合属性を定義します。
1. 複合属性を追加し、名前を付けます`colorScheme`2. そこに 3 つの String サブプロパティを追加します。`primary`、`secondary`、`tertiary`3.で`Aircraft`エンティティに追加`colorScheme`属性、タイプは次のように設定されます`colorScheme`

複合属性を設定します。

```swift
private func addAircraft() {
    viewContext.performAndWait {
        let newAircraft = Aircraft(context: viewContext)
        newAircraft.tailNumber = tailNumber
        newAircraft.aircraftType = aircraftType
        newAircraft.aircraftClass = aircraftClass
        newAircraft.aircraftCategory = aircraftCategory

        newAircraft.colorScheme = [
            "primary": primaryColor.rawValue,
            "secondary": secondaryColor.rawValue,
            "tertiary": tertiaryColor.rawValue
        ]

        do {
            try viewContext.save()
        } catch {
            // 处理错误
        }
    }
}
```

キーポイント:
- 辞書構文を使用して複合属性のサブ属性にアクセスする
- キー名はモデルエディターで定義された属性名と一致します。

キーパスを使用して複合属性をクエリします。

```swift
private func findAircraft(with color: String) {
    viewContext.performAndWait {
        let fetchRequest = Aircraft.fetchRequest()
        fetchRequest.predicate = NSPredicate(
            format: "colorScheme.primary == %@", color
        )

        do {
            let fetchedResults = try viewContext.fetch(fetchRequest)
            // ...
        } catch {
            // 处理错误
        }
    }
}
```

キーポイント:
- 使用する`colorScheme.primary`このような名前空間キーパス
- 直接行うことができます`NSPredicate`クエリのサブ属性
- これは、Transformable プロパティでは実行できないことです

複合属性はネストすることもでき、複合属性には他の複合属性を含めることができます。要素は`NSAttributeDescription`または入れ子になった`NSCompositeAttributeDescription`、関係を含めることはできません。

パフォーマンスの観点から、ほとんどの場合、エンティティを取得した後にそのリレーションシップの 1 つにアクセスする必要がある場合は、そのリレーションシップのデータを複合属性に変更できます。これにより、障害による追加のクエリが回避されます。

### Staged Migration

([07:36](https://developer.apple.com/videos/play/wwdc2023/10186/?time=456)) モデルの変更が軽量移行の機能を超える場合は、段階的移行を使用します。

中心的な考え方: 軽量ではない複雑な変更を複数のステップに分割し、軽量の移行で処理できるようにします。

シナリオ例:`Aircraft`エンティティには`flightData`バイナリ属性は独立したものに分割する必要がある`FlightData`実在物。

分解手順:
1. **ModelV1** (オリジナル):`Aircraft`持っている`flightData`プロパティ
2. **ModelV2**: 追加`FlightData`エンティティ、と`Aircraft`関係を確立し、軽量な移行を完了できる
3. **ModelV3**: 削除`Aircraft`の`flightData`プロパティ、データはカスタム コードを介して移行されました`FlightData`

モデル参照を作成します。

```swift
let v1ModelChecksum = "kk8XL4OkE7gYLFHTrH6W+EhTw8w14uq1klkVRPiuiAk="
let v1ModelReference = NSManagedObjectModelReference(
    modelName: "modelV1",
    in: Bundle.main,
    versionChecksum: v1ModelChecksum
)

let v2ModelChecksum = "PA0Gbxs46liWKg7/aZMCBtu9vVIF6MlskbhhjrCd7ms="
let v2ModelReference = NSManagedObjectModelReference(
    modelName: "modelV2",
    in: Bundle.main,
    versionChecksum: v2ModelChecksum
)

let v3ModelChecksum = "iWKg7bxs46g7liWkk8XL4OkE7gYL/FHTrH6WF23Jhhs="
let v3ModelReference = NSManagedObjectModelReference(
    modelName: "modelV3",
    in: Bundle.main,
    versionChecksum: v3ModelChecksum
)
```

キーポイント:
- `versionChecksum`使用`NSManagedObjectModel.versionChecksum`得る
- Xcode ビルド ログで「バージョン チェックサム」を検索することもできます
- バージョン管理されたモデルのチェックサムも含まれます`VersionInfo.plist`真ん中

移行ステージを作成します。

```swift
// V1 → V2 是轻量级变更（添加属性/实体）
let lightweightStage = NSLightweightMigrationStage([v1ModelChecksum])
lightweightStage.label = "V1 to V2: Add flightData attribute"

// V2 → V3 需要自定义代码迁移数据
let customStage = NSCustomMigrationStage(
    migratingFrom: v2ModelReference,
    to: v3ModelReference
)
customStage.label = "V2 to V3: Denormalize model with FlightData entity"
```

カスタマイズフェーズでデータを移行します。

```swift
customStage.willMigrateHandler = { migrationManager, currentStage in
    guard let container = migrationManager.container else {
        return
    }

    let context = container.newBackgroundContext()
    try context.performAndWait {
        let fetchRequest = NSFetchRequest<NSFetchRequestResult>(entityName: "Aircraft")
        fetchRequest.predicate = NSPredicate(format: "flightData != nil")

        do {
            let fetchedResults = try context.fetch(fetchRequest)
            for airplane in fetchedResults {
                guard let airplane = airplane as? NSManagedObject else { continue }

                let fdEntity = NSEntityDescription.insertNewObject(
                    forEntityName: "FlightData",
                    into: context
                )

                let flightData = airplane.value(forKey: "flightData")
                fdEntity.setValue(flightData, forKey: "data")
                fdEntity.setValue(airplane, forKey: "aircraft")
                airplane.setValue(nil, forKey: "flightData")
            }
            try context.save()
        } catch {
            // 处理错误
        }
    }
}
```

キーポイント:
- 使用する`NSFetchRequestResult`そして`NSManagedObject`移行時にサブクラスが存在しない可能性があるため、汎用
-`willMigrateHandler`軽量移行が完了した後、スキーマが更新される前に実行されます。
- 新しいエンティティを作成し、データをコピーし、ハンドラー内で関係を確立します。
-`didMigrateHandler`スキーマ更新後に実行 (必要な場合)

段階的移行を構成します。

```swift
let migrationStages = [lightweightStage, customStage]
let migrationManager = NSStagedMigrationManager(migrationStages)

let persistentContainer = NSPersistentContainer(
    path: "/path/to/store.sqlite",
    managedObjectModel: myModel
)

var storeDescription = persistentContainer.persistentStoreDescriptions.first
storeDescription?.setOption(
    migrationManager,
    forKey: NSPersistentStoreStagedMigrationManagerOptionKey
)

persistentContainer.loadPersistentStores { storeDescription, error in
    if let error = error {
        // 处理错误
    }
}
```

キーポイント:
- `NSStagedMigrationManager`移行プロセス全体を管理する
- パス`NSPersistentStoreStagedMigrationManagerOptionKey`ストアオプションに追加
- Core Data は各ステージを順番に自動的に実行します

### Deferred Migration

([18:56](https://developer.apple.com/videos/play/wwdc2023/10186/?time=1136)) 一部の軽量移行のクリーンアップ作業は遅れる可能性があります。

遅延移行を有効にする:

```swift
let options = [
    NSPersistentStoreDeferredLightweightMigrationOptionKey: true,
    NSMigratePersistentStoresAutomaticallyOption: true,
    NSInferMappingModelAutomaticallyOption: true
]

let store = try coordinator.addPersistentStore(
    ofType: NSSQLiteStoreType,
    configurationName: nil,
    at: storeURL,
    options: options
)
```

適切なタイミングで遅延移行を完了します。

```swift
// 通过 BGProcessingTask 在后台执行
let metadata = coordinator.metadata(for: store)
if metadata[NSPersistentStoreDeferredLightweightMigrationOptionKey] == true {
    coordinator.finishDeferredLightweightMigration()
}
```

キーポイント:
- 軽量移行自体は引き続き同期されますが、クリーンアップのみが遅延します。
- アプリは新しいスキーマをすぐに使用できます
- macOS Big Sur および iOS 14 へのフォールバックの遅延移行サポート
- SQLite ストア タイプのみをサポートします
- 適切なシナリオ: 属性/関係の削除、エンティティ階層の変更、順序付けされた関係の変更
- 推奨`BGProcessingTask`デバイスがアイドル状態のときに実行されます

### Staged + Deferred を組み合わせて使用​​する

([22:08](https://developer.apple.com/videos/play/wwdc2023/10186/?time=1328)) 複雑な移行では、両方の技術を組み合わせることができます。たとえば、例の ModelV3 は削除されます。`flightData`このクリーンアップ作業はバックグラウンドで遅れる可能性があります。

## 重要なポイント

**1.住所/連絡先の構造化ストレージ**
- **対処方法**: 複合属性を使用して、住所の都道府県、市、地区、番地を 1 つにカプセル化します。`address`プロパティ
- **実行する価値がある理由**: 4 つの独立した属性を作成するよりも直感的で、クエリ時に使用できます。`address.city == %@`直接フィルタリング
- **開始方法**: Xcode モデル エディターで複合属性を作成します。`province`、`city`、`district`、`street`4 つの文字列サブプロパティ

**2.大規模なユーザー データベースを安全に移行します**
- **内容**: 段階的移行を使用して、複雑なデータベースの変更を複数のステップに分割し、1 回限りの移行によって引き起こされる起動時のクラッシュを回避します。
- **実行する価値がある理由**: ユーザー データの量が多い場合、複雑な移行がタイムアウトしてシステムによって強制終了される可能性があるため、段階的実行の方が安定しています。
- **開始方法**: モデルの変更を分析し、軽量以外の変更を 3 つのステップに分割します:「新しい構造の追加 → データの移行 → 古い構造の削除」。各ステップでモデル バージョンを使用します。

**3.ゼロブロッキングの起動エクスペリエンス**
- **対処法**: 遅延移行を使用して、クリーニング作業をバックグラウンドで実行すると、アプリの起動後すぐに使用できるようになります。
- **実行する価値がある理由**: ユーザーがアプリを開いたときに起動画面に数秒以上留まると、道に迷ってしまいます。移行を遅らせると、起動が速くなります。
- **開始方法**: ストア オプションを追加する`NSPersistentStoreDeferredLightweightMigrationOptionKey: true`、登録する`BGProcessingTask`バックグラウンドで呼び出される`finishDeferredLightweightMigration()`

**4.変換可能属性から複合属性への移行**
- **内容**: 既存の変換可能な属性 (JSON エンコーディングを保存するカスタム タイプなど) を複合属性に徐々に置き換えます。
- **実行する価値がある理由**: Transformable はサブフィールドを直接クエリできませんが、複合属性はサポートされています。`NSPredicate`キーパス クエリ、パフォーマンスの向上
- **開始方法**: 段階的移行で新しい複合属性を作成する`willMigrateHandler`変換可能なデータを解析し、複合サブプロパティに書き込みます
