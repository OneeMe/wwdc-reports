## ハイライト

> SwiftUI のデータ フローはその中心的な設計コンセプトであり、初心者が最も混乱しやすい場所でもあります。セッション 「データ依存関係グラフ」の概念に基づいて、システムはすべてのデータ フロー関連の属性ラッパーを分類します。

---

## 主な内容

SwiftUI の `View` は有効期間が短い構造です。上位レベルの状態が変化するたびに、SwiftUI はビュー構造体を再作成し、それを使用して新しいインターフェイスを生成することがあります。開発者がデータ ライフ サイクルをビュー構造体のライフ サイクルとして理解している場合、更新、ナビゲーション、マルチウィンドウ、および非同期読み込み中に状態の損失が発生することになります。

このスピーチでは、このビューにはどのようなデータが必要なのか、データは変更されるのか、データはどこから来たのかという固定的な質問が行われます。上位層から渡されたデータのみを表示する場合は、通常の属性を使用してください。現在のビューに一時的な状態がある場合は、`@State` を使用します。サブビューが親ビューの同じ状態を変更する必要がある場合は、`@Binding` を使用します。

データがモデル層に入った時点では、`@State` だけでは十分ではありません。この講義では、読書アプリを使用して説明します。読書の進行状況、完了ステータス、表紙の読み込み、グローバル ブック リストには異なるライフ サイクルがあります。 SwiftUI はこれらのライフサイクルを `ObservableObject`、`@ObservedObject`、`@StateObject`、`@EnvironmentObject`、`@SceneStorage`、および `@AppStorage` で分離し、インターフェイスが手動でイベントをリッスンするのではなくデータに依存できるようにします。

最後の段落ではパフォーマンスに焦点を当てます。 「body」はインターフェイスのみを記述する必要があり、高価なオブジェクトを作成したり、その中でブロック作業を行ったりすることはできません。新しく導入された `@StateObject` は、ビューの初期化パスで `ObservableObject` を繰り返し作成することで更新が遅くなり、データがリセットされるというよくある間違いを解決します。

##詳細

### `@State` は、現在のビューが所有する一時的な状態を保存します

([05:09](https://developer.apple.com/videos/play/wwdc2020/10040/?time=309))

講義は読書の進捗状況を更新するシートから始まります。 `BookView` は、シートが表示されているかどうか、ユーザーのメモ、現在の進行状況を保存する必要があります。これらのフィールドは同時に変化するため、Apple はそれらを値型 `EditorConfig` に収集し、管理のためにそれらを `@State` に渡します。```swift
struct EditorConfig {
    var isEditorPresented = false
    var note = ""
    var progress: Double = 0
    mutating func present(initialProgress: Double) {
        progress = initialProgress
        note = ""
        isEditorPresented = true
    }
}
struct BookView: View {
    @State private var editorConfig = EditorConfig()
    func presentEditor() { editorConfig.present(…) }
    var body: some View {
        …
        Button(action: presentEditor) { … }
        …
    }
}
```キーポイント:

- `EditorConfig` は 3 つの関連フィールドをまとめているため、進行状況、メモ、表示ステータスが複数のプロパティに分散されることはありません。
- `present(initialProgress:)` は、値自体に対して更新が発生することを示す `mutating` メソッドです。
- `@State` は、SwiftUI にこのストレージを管理するように指示します。ビュー構造体が再作成されると、SwiftUI は既存の状態に再接続します。
- `presentEditor()` は `EditorConfig` に状態の更新を要求するだけであり、インターフェースの更新は状態の変化に応じて SwiftUI によって完了します。

### `@Binding` 同じ状態を変更のためにサブビューに渡します

([07:22](https://developer.apple.com/videos/play/wwdc2020/10040/?time=442))

「ProgressEditor」は「BookView」の「EditorConfig」を変更する必要があります。値を直接渡すと、サブビューはコピーにのみ変更されます。サブビューが独自の `@State` を宣言すると、2 つ目の信頼できる情報源が生成されます。 `@Binding` の機能は、親ビューステートの読み取りおよび書き込みエントリを渡すことです。```swift
struct EditorConfig {
    var isEditorPresented = false
    var note = ""
    var progress: Double = 0
}
struct BookView: View {
    @State private var editorConfig = EditorConfig()
    var body: some View {
        …
        ProgressEditor(editorConfig: $editorConfig)
        …
    }
}

struct ProgressEditor: View {
    @Binding var editorConfig: EditorConfig
    …
        TextEditor($editorConfig.note)
    …
}
```キーポイント:

- `$editorConfig` は `@State` から投影された値、タイプは `Binding<EditorConfig>` です。
- `ProgressEditor` は `@Binding` を受け取ると、`BookView` が所有する同じ状態を変更します。
- `TextEditor` 自体もバインディングを受け取ります。`$editorConfig.note` は既存のバインディングから派生した文字列バインディングです。
- バインディングは特定のソースから独立しています。これは、`@State` から取得することも、基礎となるモデル オブジェクトやストレージ ラッパーから取得することもできます。

### `ObservableObject` はモデルの変更をビューに公開します

([13:15](https://developer.apple.com/videos/play/wwdc2020/10040/?time=795))

この講演では、データの永続化、同期化、または副作用の処理が必要な場合にモデル層に入ることが推奨されています。 `ObservableObject` は、オブジェクトが `objectWillChange` パブリッシャーを通じて変更されようとしていることを SwiftUI に伝える、クラス制約のあるプロトコルです。これを記述する一般的な方法は、変更されるプロパティに `@Published` を置くことです。```swift
/// The current reading progress for a specific book.
class CurrentlyReading: ObservableObject {
    let book: Book
    @Published var progress: ReadingProgress

    // …
}

struct ReadingProgress {
    struct Entry : Identifiable {
        let id: UUID
        let progress: Double
        let time: Date
        let note: String?
    }

    var entries: [Entry]
}
```キーポイント:

- `CurrentlyReading` は、特定の書籍の読書状況を管理するために使用される参照型です。
- 本自体はスピーチ中に変更されないため、「book」には「let」を使用します。
- `progress` は `@Published` を使用するため、レコードの変更を読み取る前に SwiftUI の依存関係の更新がトリガーされます。
- `ReadingProgress` は依然として値タイプです。この講演では、値型を使用してデータをモデル化し、参照型を使用してライフサイクルと副作用を管理できることが明確になりました。

### `@ObservedObject` は外部モデルを参照し、`@StateObject` はモデルのライフサイクルを所有します

([15:36](https://developer.apple.com/videos/play/wwdc2020/10040/?time=936))

`@ObservedObject`は外部から渡された`ObservableObject`を読み込むのに適しています。これにより、SwiftUI はオブジェクトの `objectWillChange` をサブスクライブしますが、このインスタンスを作成して維持する責任はありません。```swift
struct BookView: View {
    @ObservedObject var currentlyReading: CurrentlyReading

    var body: some View {
        VStack {
            BookCard(
                currentlyReading: currentlyReading)

            //…

            ProgressDetailsList(
                progress: currentlyReading.progress)
        }
    }
}
```キーポイント:

- `currentlyReading` はこのビューの信頼できる情報源ですが、インスタンスのライフサイクルは外部で管理されます。
- `BookCard` と `ProgressDetailsList` はどちらも同じオブジェクトからデータを読み取り、変更されたときに一緒に更新します。
- ビューは、データがインターフェイスにどのようにマップされるかを宣言するだけであり、手書きのサブスクリプション コードや更新コードは必要ありません。

([20:20](https://developer.apple.com/videos/play/wwdc2020/10040/?time=1220))

`@StateObject` は 2020 年の新機能です。これは、ビューが ObservableObject を持つのに適しています。この講義では例としてカバー ローダーを使用します。カバーはビューが表示されている場合にのみ必要であり、ローダーはビューのライフ サイクルに従って作成およびリリースされる必要があります。```swift
struct BookCoverView: View {
    @StateObject var loader = CoverImageLoader()

    var coverName: String
    var size: CGFloat

    var body: some View {
        CoverImage(loader.image, size: size)
            .onAppear { loader.load(coverName) }
    }
}
```キーポイント:

- `@StateObject` は、初めて `body` を実行する前に SwiftUI がインスタンス化する初期値を提供します。
- SwiftUI は、ビュー構造が再構築されるときにオブジェクトが失われないように、ビューのライフサイクル全体を通じて「ローダー」を保持します。
- `onAppear` は読み込みアクションのみをトリガーします。オブジェクトが解放されると、`CoverImageLoader` 自体が `deinit` での作業をキャンセルできます。

([26:39](https://developer.apple.com/videos/play/wwdc2020/10040/?time=1599))

このスピーチでは、「@ObservedObject」プロパティに直接「ReadingListStore()」を作成するという間違った書き方を具体的に比較していました。ビュー構造体には安定したライフサイクルがないため、「body」が再構築されるときに繰り返しオブジェクトが割り当てられ、更新の遅延とデータ損失が発生します。修正方法は、代わりに `@StateObject` を使用することです。```swift
struct ReadingListViewer: View {
    var body: some View {
        NavigationView {
            ReadingList()
            Placeholder()
        }
    }
}

struct ReadingList: View {
    @StateObject var store = ReadingListStore()

    var body: some View {
        // ...
    }
}
```キーポイント:

- `ReadingListStore` は、`ReadingList` が所有する信頼できる情報源です。
- `@StateObject` を使用すると、SwiftUI は適切なタイミングでオブジェクトを作成し、ビューの存続期間中それを永続化できます。
- この修正により、ヒープ割り当ての繰り返しとオブジェクトのリセットという 2 つの問題が同時に解決されます。

### `@SceneStorage` と `@AppStorage` は軽量 UI 状態を保存します

([32:43](https://developer.apple.com/videos/play/wwdc2020/10040/?time=1963))

`@State` と `@StateObject` のライフサイクルはプロセスに関連しています。アプリがシステムによって終了された後は、自動的には復元されません。このスピーチでは、軽量状態を保存するために使用される「Storage」ファミリーが紹介されています。 `@SceneStorage` は、列インターフェイスで現在選択されているブックなど、独立して保存される各シーンに適しています。```swift
struct ReadingListViewer: View {
    @SceneStorage("selection") var selection: String?

    var body: some View {
        NavigationView {
            ReadingList(selection: $selection)
            BookDetailPlaceholder()
        }
    }
}
```キーポイント:

- `"selection"` はストレージキーです。同じ種類のデータには、安定した一意のキーが必要です。
- `selection` は `@State` と同様に使用でき、バインディングは `$selection` を通じて生成することもできます。
- 各シーンは、iPad または Mac 上の複数のウィンドウに適した独自の選択状態を持つことができます。

([33:49](https://developer.apple.com/videos/play/wwdc2020/10040/?time=2029))

`@AppStorage` は、`UserDefaults` を使用して小さなアプリレベルのデータを保存します。音声の例は、表紙画像を更新するかどうかと読書の進行状況を同期するかどうかの 2 つの設定スイッチです。```swift
struct BookClubSettings: View {
    @AppStorage("updateArtwork") private var updateArtwork = true
    @AppStorage("syncProgress") private var syncProgress = true

    var body: some View {
        Form {
            Toggle(isOn: $updateArtwork) {
                //...
            }

            Toggle(isOn: $syncProgress) {
                //...
            }
        }
    }
}
```キーポイント:

- 各設定は 2 つの独立したデータであるため、独自のキーを使用します。
- `@AppStorage` は、デフォルトで標準ユーザーのデフォルトを使用します。
- バインディングを通じて設定値を変更すると、SwiftUI が自動的に保存および復元します。
- このスピーチでは、永続化にはコストがかかるため、すべてのデータをストレージ ラッパーに詰め込まないように注意を促しています。

## 重要なポイント

1. **読書進捗エディタ**: **機能**: 読書、コース、またはフィットネス アプリのメモを含む進捗更新シートを作成します。 **実行する価値がある理由**: このセッションの `EditorConfig` は、複数の関連フィールドを 1 つの `@State` 値に収集する方法を示しています。 **開始方法**: まず値型構成オブジェクトを定義し、次に `$editorConfig` を編集サブビューに渡します。

2. **カバーまたはアバターの読み込みビュー**: **何をすべきか**: ネットワーク イメージ ローダーを独立した SwiftUI ビューにカプセル化します。 **実行する価値がある理由**: `@StateObject` を使用すると、ローダーがビューのライフサイクルに従って生き続けることができるため、割り当てと状態のリセットの繰り返しが減ります。 **開始方法**: ローダーを `ObservableObject` に準拠させ、ビュー内の `@StateObject` で作成し、 `onAppear` で読み込みをトリガーします。

3. **マルチウィンドウの選択状態の復元**: **何をするか**: iPad または Mac のリスト詳細インターフェイスで各ウィンドウの現在の選択を復元します。 **実行する価値がある理由**: `@SceneStorage` はシーンごとのストレージであり、軽量の UI 状態の保存に適しています。 **開始方法**: 選択値の一意のキーを定義し、`$selection` をリスト ビューに渡します。

4. **軽量設定ページ**: **何をするか**: 同期するかどうか、表紙を更新するかどうか、特定の領域を表示するかどうかなどのスイッチを実装します。 **実行する価値がある理由**: `@AppStorage` は `UserDefaults` に直接接続しており、小規模なアプリレベルの設定に適しています。 **開始方法**: 各設定の `@AppStorage` プロパティを宣言し、バインディングを `Toggle` に渡します。

5. **グローバル データ入力**: **何をすべきか**: 書籍リスト、アカウント ステータス、または現在のワークスペース モデルを SwiftUI アプリのルートに置きます。 **実行する価値がある理由**: このスピーチでは、すべてのシーンがモデルの変更に対応できるように、「@main App」の「@StateObject」を使用してアプリ全体の信頼できる情報源を作成する方法が示されました。 **開始方法**: アプリ タイプで `@StateObject private var store` を宣言し、ストアをルート ビューまたはインジェクション環境に渡します。
