## ハイライト

> AppleSeed for IT 让企业和学校用 Managed Apple ID 参与预发布系统测试并通过 Feedback Assistant Teams 协作反馈，macOS Big Sur 同时把软件更新延迟、扫描、状态查询和安装调度纳入 MDM 管理面。

## 主要内容

企业 IT 最怕系统发布日才发现问题。内部网络、第三方 MDM、业务关键 App、VPN、身份系统和受管设备组合在一起，任何一处兼容性问题都可能拖住升级。Apple 在开场直接说明，它无法复制每个企业和学校的真实环境，所以预发布测试必须由组织自己参与。（[00:39](https://developer.apple.com/videos/play/wwdc2020/10138/?time=39)）

AppleSeed for IT 的定位就在这里。Public Beta 面向普通用户，Developer Program 面向 App 开发者，AppleSeed for IT 面向企业和教育 IT。这个计划提供面向 IT 管理流程的 beta 文档、release notes、测试计划和调查，让组织在正式发布前验证自己的基础设施、关键 App 和服务。（[02:11](https://developer.apple.com/videos/play/wwdc2020/10138/?time=131)）

测试发现问题后，反馈也要能被团队承接。过去，反馈常常跟着提交人走：同事离职或休假，问题上下文就散掉。iOS 14、iPadOS 14 和 macOS Big Sur 的 Feedback Assistant Teams 允许团队成员看到彼此提交的反馈、Apple 的回复，并在需要时重新分配负责人。（[05:41](https://developer.apple.com/videos/play/wwdc2020/10138/?time=341)）

后半场把测试延伸到发布控制。组织理想上应该尽快部署 Apple 更新，因为更新包含稳定性、性能和安全修复；现实里，IT 往往需要短时间认证最终版本。Managed Software Updates 给出的解法是：用 MDM 控制可见更新、扫描更新状态、安排下载或安装，再通过尽量短的延迟窗口完成认证和分阶段推广。（[13:00](https://developer.apple.com/videos/play/wwdc2020/10138/?time=780)）

## 詳細

### AppleSeed for IT 的参与流程

（[03:07](https://developer.apple.com/videos/play/wwdc2020/10138/?time=187)）加入 AppleSeed for IT 不再需要单独的消费者账号流程。参与者使用 Managed Apple ID 登录，接受项目条款，然后把测试设备配置为接收预发布更新。

```text
1. Use a Managed Apple ID.
2. Sign in at appleseed.apple.com.
3. Accept the AppleSeed for IT program terms.
4. Configure test devices with the configuration profile or the macOS Customer Beta Access Utility.
5. File deployment blockers and regressions through Feedback Assistant.
```

キーポイント:

- Managed Apple ID 由 Apple Business Manager 或 Apple School Manager 管理，适合企业和学校把测试身份纳入组织账号体系。
- 配置文件和 macOS Customer Beta Access Utility 都来自 AppleSeed 下载页，目标是让指定测试设备收到预发布版本。
- Apple 明确希望收到 deployment blockers 和 regressions，也就是会阻止部署的问题，以及预发布版本相对上一个正式版退化的问题。

（[04:43](https://developer.apple.com/videos/play/wwdc2020/10138/?time=283)）提交反馈时，时间点、复现步骤、屏幕录制、截图和相关日志都很关键。Apple 还为企业和教育配置提供额外 profile，用来采集更贴近组织环境的日志。

### Feedback Assistant Teams

（[05:41](https://developer.apple.com/videos/play/wwdc2020/10138/?time=341)）Teams 是 Feedback Assistant 在当年系统版本中的协作更新。团队空间由 Apple Business Manager 或 Apple School Manager 为 AppleSeed for IT 配置，Developer Program 则通过 App Store Connect 配置。

```text
Create team feedback -> teammates can see it -> Apple can respond -> current assignee or admin can reassign -> team verifies fixes together
```

キーポイント:

- 团队成员可以看到队友创建的反馈、Apple 的回复，以及后续来回沟通。
- 反馈可以从个人空间移动到团队空间，避免历史问题只留在提交人的账号里。
- 负责人离开团队后，管理员可以重新分配反馈；管理员还可以把反馈移出团队或关闭队友的反馈。

（[06:26](https://developer.apple.com/videos/play/wwdc2020/10138/?time=386)）multi-device diagnostics 解决的是另一类常见问题：Continuity、AirDrop、同步这类跨设备功能往往需要多台设备的日志。新的 Feedback Assistant 可以从同一 iCloud 账号下的其他设备远程收集诊断，并允许先提交反馈，诊断完成后再由设备上传给 Apple。

### iOS、iPadOS 和 tvOS 的更新延迟

（[14:51](https://developer.apple.com/videos/play/wwdc2020/10138/?time=891)）在 iOS、iPadOS 和 tvOS 上，软件更新延迟由 MDM 控制，可以通过 profile 部署到受监督设备。默认延迟窗口是 Apple 发布更新后的 30 天，管理员可以改成 1 到 90 天。

```text
iOS / iPadOS / tvOS deferral
- target: supervised devices
- default: 30 days from Apple release
- configurable: 1-90 days
- basis: release date, not release version number
```

キーポイント:

- 延迟窗口按日期计算，不按版本号计算；窗口过期后，系统会重新评估下一个更新是否显示给用户。
- 已安装更新后，Apple 不支持在不抹掉设备的情况下回退到旧系统。
- 设备只能安装 Apple 仍在签名的版本，这是为了避免 downgrade attacks。

### macOS 的托管更新能力

（[16:26](https://developer.apple.com/videos/play/wwdc2020/10138/?time=986)）macOS 的 Software Update 管理面覆盖系统更新，也覆盖 Safari 这类 out-of-band updates。MDM 可以安排扫描、获取可用更新列表、读取更新进度，并安排安装。

```text
macOS managed update workflow
1. Schedule a scan across the Mac fleet.
2. Fetch the list of available updates.
3. Read the status of updates in progress.
4. Schedule eligible updates for installation.
```

キーポイント:

- 远程管理更新需要受监督设备；但 macOS 上单纯延迟软件更新时，可以通过配置 profile 控制，不要求设备受监督。
- 管理员可以让 Software Update 偏好设置保留为用户选择，也可以通过 MDM 完全接管这些设置。
- macOS 的延迟窗口同样最长 90 天，更新过了窗口后会在 System Preferences 里重新对用户可见。

（[19:30](https://developer.apple.com/videos/play/wwdc2020/10138/?time=1170)）macOS Big Sur 增加了在 seeding 期间延迟软件更新的支持。macOS Catalina 10.15.4 起，Apple 也把 major releases 纳入同一套延迟窗口。Apple 的建议很明确：在 beta 阶段完成验证，正式版发布后只使用短延迟来认证最终构建。

### Big Sur 安装与安全变化

（[20:04](https://developer.apple.com/videos/play/wwdc2020/10138/?time=1204)）Big Sur 的安装技术向 iOS 靠拢。系统会 snapshot system volume，并用 authenticated APFS 对 snapshot 做加密封签；启动时会校验系统是否匹配 Apple 交付的内容。

```text
Big Sur update model
- unified installation technology across Apple platforms
- system volume snapshots
- authenticated APFS sealing
- server-driven OS update qualification
- Apple-managed installation catalog
```

キーポイント:

- snapshot patching 让用户使用 Mac 时也能进行系统 snapshot 更新准备。
- authenticated APFS 会沿文件系统链路校验 hash；root hash 不匹配时，seal 被视为破坏。
- Big Sur 移除了第三方 software update catalogs，并停止支持无限期忽略更新；Apple 鼓励组织使用有限期 deferral 和预发布测试组合完成治理。

## 重要ポイント

- **预发布系统验证清单**：做什么：为每个 beta 建一张 IT 验证表，覆盖 MDM、身份登录、VPN、关键 App、打印、同步和课堂设备。为什么值得做：AppleSeed for IT 的目标就是发现 deployment blockers 和 regressions。怎么开始：用 Managed Apple ID 加入 AppleSeed，在第一批测试设备上安装 profile，再把每个阻塞问题提交到 Feedback Assistant。

- **团队反馈工作台**：做什么：把组织内的 beta 问题按团队空间、负责人、Apple 回复和待验证状态整理出来。为什么值得做：Teams 让反馈不再只属于提交人，适合处理跨部门问题和人员变动。怎么开始：在 Apple Business Manager 或 Apple School Manager 检查 AppleSeed for IT 权限，把历史个人反馈移动到 team space，并约定谁负责验证 Apple 标记为 fixed 的问题。

- **90 天内的更新发布日历**：做什么：为 iOS、iPadOS、tvOS 和 macOS 制定从 Apple 发布日开始计算的延迟窗口。为什么值得做：session 明确说 deferral 按日期生效，窗口范围是 1 到 90 天。怎么开始：把关键部门分成测试组、早期组和全量组，在 MDM 中设置尽量短的延迟，并配合 content caching 降低网络压力。

- **Mac 更新状态看板**：做什么：展示 fleet 中每台 Mac 的可用更新、安装进度和是否已过延迟窗口。为什么值得做：macOS 的 MDM 管理面支持扫描、获取可用更新、读取进度和安排安装。怎么开始：先用现有 MDM 的 software update 报告能力收集状态，再把未扫描、待安装和安装中的设备分桶处理。

- **Big Sur 兼容性验收流程**：做什么：把系统卷封签、第三方 update catalog 移除、无限期忽略更新失效这些 Big Sur 变化列为验收项。为什么值得做：这些变化会直接影响 Mac 管理、运维脚本和历史更新流程。怎么开始：挑选一组受管 Mac 进入 seeding 测试，验证启动、更新、回滚预期和管理策略，再决定正式发布后的延迟天数。
