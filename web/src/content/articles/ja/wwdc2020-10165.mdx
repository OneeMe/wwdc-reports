## ハイライト

> Apple は、Fruta の SwiftUI 検索リストを使用して、Swift の型推論が配列、KeyPath、クロージャー、ViewBuilder からジェネリック パラメーターを推定する方法を示し、Xcode 12 が式エラーをメモと Fix-It を使用して診断に変換する方法を説明します。

## 主要内容

多くの型情報が呼び出しサイトのコンテキストに隠されているため、SwiftUI コードは短く見えます。リスト、フィルター条件、行ビュー クロージャ (ジェネリック パラメータ、KeyPath、エスケープ クロージャ、および`@ViewBuilder`。開発者がすべての型を手動で記述した場合、コードは山括弧、型変換、およびクロージャー パラメーターの注釈で埋め尽くされてしまいます。

このセッションにはスムージーアプリ「Fruta」が選ばれました。ホリーはリストに検索を追加したいと考えています。ユーザーが文字列を入力すると、タイトルにその文字列が含まれるスムージーのみがリストに表示されます。彼女はフィルタリング ロジックを直接挿入しませんでした。`List`、しかし再利用可能なものを書きました`FilteredList`、呼び出し元がデータ、フィルタリング プロパティ、フィルタリング関数、および行ビューを渡すことができるようにします。

重要なのはコールポイントです。`FilteredList(smoothies, filterBy: \.title, isIncluded: { title in ... }) { smoothie in ... }`書かれていない`Element`、`FilterKey`、`RowContent`。コンパイラは次から起動します`smoothies`ロールアウトする`Element == Smoothie`、そしてから`\.title`ロールアウトする`FilterKey == String`、最後に後続の ViewBuilder クロージャーから押し出されます。`RowContent == SmoothieRowView`。

Xcode 12 では、型推論エラーが発生した場合の変更もあります。 Swift 5.3 は、統合されたエラー追跡を式内のすべてのエラーに拡張します。コンパイラは推論中に発生した問題を記録し、メモを使用して関連する宣言を示し、fix-it を使用して一般的なエラー (パスの受け渡しなど) を修正します。`TextField`文字列値をバインディングに変更します。

## 詳細

### 1. 呼び出しポイントはコンパイラーに十分な手がかりを残します

([02:56](https://developer.apple.com/videos/play/wwdc2020/10165/?time=176)) フルッタの`SmoothieList`検索語を保存する`@State`、そしてオリジナルを置きます`List`と置き換えます`FilteredList`。この公式コードは、呼び出しサイトをシンプルに保つ方法を示しています。

```swift
import SwiftUI

struct SmoothieList: View {
    var smoothies: [Smoothie]

    @State var searchPhrase = ""

    var body: some View {
        FilteredList(
            smoothies,
            filterBy: \.title,
            isIncluded: { title in title.hasSubstring(searchPhrase) }
        ) { smoothie in
            SmoothieRowView(smoothie: smoothie)
        }
    }
}

extension String {
    /// Returns `true` if this string contains the provided substring,
    /// or if the substring is empty. Otherwise, returns `false`.
    ///
    /// - Parameter substring: The substring to search for within
    ///   this string.
    func hasSubstring(_ substring: String) -> Bool {
        substring.isEmpty || contains(substring)
    }
}
```

キーポイント:

- `smoothies`既知のタイプは次のとおりです`[Smoothie]`、それは与えます`Element`この一般的なパラメータが最初の手がかりとなります。
-`filterBy: \.title`基本型は書き込まれません。`Element`すでにコンパイラにこれがであることを知らせています`Smoothie.title`。
- `isIncluded`閉店中`title`による`FilterKey`として発売されました`String`, だからあなたは電話することができます`hasSubstring`。
- トレーリングクロージャーが戻る`SmoothieRowView`、これは`RowContent`コンクリートタイプ。
-`@State var searchPhrase = ""`コンパイラが空の文字列から推論するリテラル推論にも依存します。`String`。

### 2. 再利用可能なコンポーネントは宣言内に型の関係を記述します

（[03:53](https://developer.apple.com/videos/play/wwdc2020/10165/?time=233)）`FilteredList`宣言では、呼び出しポイントから省略される型の関係を明確に示します。汎用パラメーターは、それぞれデータ要素、フィルター フィールド、行ビューのコンテンツを表します。

```swift
import SwiftUI

public struct FilteredList<Element, FilterKey, RowContent>: View
        where Element: Identifiable, RowContent: View {

    private let data: [Element]
    private let filterKey: KeyPath<Element, FilterKey>
    private let isIncluded: (FilterKey) -> Bool
    private let rowContent: (Element) -> RowContent

    public init(
        _ data: [Element],
        filterBy key: KeyPath<Element, FilterKey>,
        isIncluded: @escaping (FilterKey) -> Bool,
        @ViewBuilder rowContent: @escaping (Element) -> RowContent
    ) {
        self.data = data
        self.filterKey = key
        self.isIncluded = isIncluded
        self.rowContent = rowContent
    }

    public var body: some View {
        let filteredData = data.filter {
            isIncluded($0[keyPath: filterKey])
        }

        return List(filteredData, rowContent: rowContent)
    }
}
```

キーポイント:

- `Element`に制約されています`Identifiable`、最終的には SwiftUI に引き渡されるため`List`展示する。
-`FilterKey`から`KeyPath<Element, FilterKey>`これにより、コンポーネントが任意のフィールドをフィルターできるようになります。
-`isIncluded`引き継ぐ`FilterKey`そして戻る`Bool`の場合、呼び出しポイントは「このフィールドの値が保持されるかどうか」を記述するだけで済みます。
-`rowContent`引き継ぐ`Element`そして戻る`RowContent`，`where RowContent: View`戻り値が SwiftUI ビューになれることを確認します。
-`@ViewBuilder`コール ポイントで SwiftUI DSL 構文を使用すると、ViewBuilder はクロージャ内の子ビューを親ビューに必要な構造に収集します。

### 3. 型推論は制約を解くようなものであり、型を推測するものではありません

([08:43](https://developer.apple.com/videos/play/wwdc2020/10165/?time=523)) このトークでは、型推論をパズルとして説明しています。コンパイラは最初に検索します`smoothies`、クイック ヘルプで知られています。`[Smoothie]`、それですべて`Element`プレースホルダーを次のように置き換えます`Smoothie`。この結果により、`\.title`なる`Smoothie.title`, クイックヘルプでそれが示されています`String`、それから`FilterKey`なる`String`。最後に、ViewBuilder クロージャには 1 つだけあります。`SmoothieRowView`、それで`RowContent`なる`SmoothieRowView`。

このシーケンスは、呼び出しサイトを記述する必要がない理由を説明しています。

```swift
// これらの型は呼び出しサイトのコンテキストから手がかりが得られるため、実際のコードで手書きする必要はありません。
Element == Smoothie
FilterKey == String
RowContent == SmoothieRowView
```

キーポイント:

- コンパイラーは既存の型から推論を開始し、新しい結論がその後の手がかりを解き明かし続けます。
-`Element`特定されると、すべての出来事が`Element`すべての場所で同じコンクリート タイプが使用されます。
-`FilterKey`ソースは`KeyPath`指定された属性の型、クロージャー パラメーター名は、この推論された型を継承するだけです。
-`RowContent`ViewBuilder クロージャからの結果の型。
- プレースホルダーに手がかりが一致しない型で埋められている場合、推論は完了できず、ソース コードにエラーが発生します。

### 4. Xcode 12 は推論の失敗を追跡可能な診断に変換します

([11:31](https://developer.apple.com/videos/play/wwdc2020/10165/?time=691)、[14:00](https://developer.apple.com/vi deos/play/wwdc2020/10165/?time=840)、 [15:46](https://developer.apple.com/videos/play/wwdc2020/10165/?time=946)) キー パスが間違った属性に書き込まれた場合、コンパイラは`FilterKey`所定の位置に押し込みます`Bool`。次`isIncluded`クロージャで呼び出される`hasSubstring`時間、`Bool`このメソッドを使用しないと、式は失敗します。

Xcode 12 の改良点がここにあります。 Swift コンパイラーは、型推論中のエラーをログに記録し、ヒューリスティックを使用して推論を継続し、最後に収集したエラー、修正、メモをレポートします。スピーチの具体例は次の 2 つです。`TextField`コンパイラによって提供されるバインディングが必要です`$`参照バインディングの修正。`Smoothie`満たさない`Identifiable`、メモに戻ります。`FilteredList`宣言する、参照`where Element: Identifiable`この制約。

```swift
public struct FilteredList<Element, FilterKey, RowContent>: View
        where Element: Identifiable, RowContent: View
```

キーポイント:

- `Identifiable`制約はそこにはありません`SmoothieList`コールポイントでは通知されますが、メモを通じて返されます`FilteredList`声明。
- コンパイラーによって記録された推論された具象型が診断に表示されます。たとえば、`Element`押し込まれた`Smoothie`。
- Issue Navigator は、プロジェクト全体のビルドの失敗を表示するのに適しています。 Option+Shift をクリックしてメモをクリックすると、関連ファイルが並べて開きます。
- クイック ヘルプでは、次のような特定のパラメータの推定タイプを確認できます。`\.title`対応する`String`。
- 空の文字列を使用し、`"Berry"`2 セットの検索語によりキャンバスが更新され、フィルタリング ロジックが実際に推測された型に従って動作することが確認されます。

## 重要ポイント

### 1. 入力された検索リストを作成する

**何をすべきか**: リスト検索を類似のものに抽出します。`FilteredList`呼び出し元が配列、フィルター フィールド、フィルター条件、行ビューを渡すことができる再利用可能な SwiftUI コンポーネント。

**実行する価値がある理由**: セッション ショー`Element`、`FilterKey`、`RowContent`呼び出し元が SwiftUI ネイティブに近い状態を維持できるように、呼び出しポイントから自動的に推論する方法`List`書き方。

**開始方法**: まずは質問してください`Element: Identifiable`、フィールドエントリを次のように設計します。`KeyPath<Element, FilterKey>`、フィルター クロージャは次のように記述されます。`(FilterKey) -> Bool`、行閉鎖プラス`@ViewBuilder`。

### 2. チームコンポーネントのより明確な一般的な境界を設計する

**対処方法**: SwiftUI の内部コンポーネントを調べて、「呼び出しサイトで記述する型」と「宣言で表現される型の関係」を分離します。

**そうする価値がある理由**: スピーチでのコールポイントが簡潔である理由は次のとおりです。`FilteredList`初期化パラメータは、データ、KeyPath、フィルタ クロージャ、および行クロージャ間の関係を完全に表現します。

**開始方法**: 繰り返しビュー コンポーネントから始めて、実際に必要な 3 つのタイプ (入力データ、構成に使用されるフィールド、最終的に生成されるビュー) をリストします。次に、これらの型を汎用パラメータに入れて、`where`制約。

### 3. コンパイラ ノートをデバッグ プロセスに組み込む

**やるべきこと**: Swift ビルドの失敗処理の一連の習慣を確立します。Issue Navigator を開き、最初に fix-it を確認し、次にメモで示されている宣言ファイルを確認します。

**実行する価値がある理由**: Swift 5.3 と Xcode 12 では、式の型推論でより多くのエラー コンテキストがログに記録され、「この制約が現在の呼び出しサイトに関連する理由」を説明するメモが付けられます。

**開始方法**: Xcode の動作でビルドが失敗した場合の問題ナビゲーターを設定します。一般エラーまたは SwiftUI エラーが発生した場合は、Option+Shift を使用してメモで示された場所を開き、呼び出しポイントに戻って問題を修正します。

### 4. 型推論後にプレビューを使用して実際のパスを上書きします

**何をすべきか**: 空の検索用語や ViewBuilder など、ジェネリックスと ViewBuilder に依存するコンポーネントの SwiftUI プレビューの複数のセットを補足します。`"Berry"`検索語。

**実行する価値がある理由**: 最後に、セッションはプレビュー プロバイダーを使用して 2 セットの検索フレーズを同時に実行して検証します。`FilteredList`推論された型、フィルター関数、および rowContent クロージャーは正しく連携して機能します。

**開始方法**: プレビュー プロバイダー用の一連の固定入力を準備し、主要な状態を列挙し、内部ロジックをテストするために呼び出しポイントを個別にバイパスするのではなく、状態ごとにコンポーネントの実際の初期化子を 1 回実行します。
