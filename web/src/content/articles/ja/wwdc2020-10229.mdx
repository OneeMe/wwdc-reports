## ハイライト

> 低遅延 HLS ではプレイリストのリリースが必要`#EXT-X-PRELOAD-HINT`これにより、クライアントが次の部分セグメントを事前にリクエストし、サーバーがセグメントが利用可能になるとすぐにそれを返すことができるため、メディアが検出された後の追加の往復遅延が削減されます。

## 主な内容

ライブ ブロードキャストの低レイテンシーのボトルネックは、小さな隙間に隠れていることがよくあります。プレイリストが更新された後、クライアントは新しいシャードの URI だけを知っており、メディア リクエストを開始します。クロスリージョン CDN シナリオでは、エッジ ノードからオリジンまでの往復に 100 ミリ秒以上かかる場合があります。目標遅延がわずか数秒であるライブ ブロードキャストの場合、この差は繰り返し蓄積されます。

プレイリストのリロードをブロックすることで、プレイリストの検出の問題が解決されました。クライアントは事前に次のプレイリスト バージョンをリクエストでき、サーバーはプレイリストが更新されるのを待ってから戻ります。プリロード ヒントのブロックは、同じ考え方をメディア シャーディング自体に適用します。プレイリストは最初に次の部分セグメントのヒントを書き込み、クライアントはすぐにこの URL をリクエストし、セグメントのエンコードとパッケージ化が完了した後にサーバーがデータを返します。

その結果、メディアはリクエストを開始する前に「新しいシャードが見つかる」まで待機する必要がなくなりました。通常、クライアントはブロッキング プレイリスト リロード リクエストとプリロード ヒント リクエストを同時にハングさせます。新しい部分セグメントが完了すると、サーバーはプレイリストを更新し、メディア リクエストを解放します。プレーヤーがプレイリストの更新を取得するまでに、メディア データはすでに送信されています。

このセッションでは、2 つの配信モデルについても説明します。単純なモデルでは、各部分セグメントは独立した URL を持ちます。 CMAF チャンク モデルでは、複数の部分セグメントは同じ親セグメントのバイト範囲です。クライアントはチャンク転送を使用して、1 つのリクエストから複数のチャンクを継続的に受信できます。これにより、同じメディア セットから低遅延 HLS と低遅延 DASH の両方を提供することが容易になります。

＃＃詳細

### 次の部分セグメントを事前にリクエストします

([00:48](https://developer.apple.com/videos/play/wwdc2020/10229/?time=48)) プリロード ヒンティングの目的は、メディアが実際に利用可能になる前にリクエストを確立することです。プレイリストは必ず持参してください`#EXT-X-PRELOAD-HINT`、それ`URI`パッケージャーが生成すると予想される次の部分セグメントを指します。

```text
已发布的最后一个 Partial Segment：part1.1.m4s
Preload Hint 指向 packager 预计生成的下一个 Partial Segment：part1.2
```

キーポイント:

- トランスクリプトには、最後に公開された部分が次であることが明示的に記載されています。`part1.1.m4s`。
- トランスクリプトでは、ヒントがクライアントにロードを試行できる次の部分であることを伝えると明示的に述べられています。`part1.2`。
- `TYPE=PART`メディアの部分セグメントのセマンティクスに使用されるプリロード ヒントです。
- クライアントはヒントを見た後、すぐにヒントされた URL をリクエストします。シャードがまだ生成されていない場合、サーバーは要求を続け、シャードが使用可能になった後に戻ります。

([02:30](https://developer.apple.com/videos/play/wwdc2020/10229/?time=150)) 実際のリクエスト フローは非常に簡単です。クライアントは最初にブロッキング プレイリスト リロードを開始し、次にヒント付き部分セグメント リクエストを開始します。エンコーダーが新しい部分セグメントを完了すると、サーバーはメディア応答を解放し、プレイリストを更新します。プレーヤーは、「プレイリストを受信して​​からメディアを要求する」という待ち時間を節約できます。

### コンテンツの切り替えを事前に処理するよう MAP に指示する

([02:15](https://developer.apple.com/videos/play/wwdc2020/10229/?time=135)) プリロードヒントは、今後の`MAP`。これは、プレーヤーが事前に新しい初期化情報を取得し、切り替えポイントでの一時停止を減らすことができるため、広告境界などのコンテンツ切り替えにとって重要です。

```text
内容切换前：playlist 可以提示即将出现的 MAP。
内容切换后：playlist 继续提示下一个 Partial Segment。
```

キーポイント:

- トランスクリプト記述のプリロード ヒントは、今後の MAP タグに使用できます。
・ MAP ヒントの目的は、コンテンツの切り替えに必要な初期化情報をクライアントが事前に準備できるようにすることです。
- コンテンツ境界では、クライアントは引き続き後続の部分セグメントの読み込みを続けます。
- クリエイティブが事前に記録されたコンテンツの場合、サーバーはライブ エンコードされたコンテンツのようにブロックしたり待機したりすることなく、ヒント リクエストをすぐに返すことができます。

### バイト範囲を使用して部分セグメントを表現します

([03:39](https://developer.apple.com/videos/play/wwdc2020/10229/?time=219)) 部分セグメントには必ずしも独立したファイルがあるとは限りません。より大きなリソースではバイト範囲になることもあります。プリロードヒントタグを持ち込める`BYTERANGE-START`そして`BYTERANGE-LENGTH`。長さが決まっていない場合は、開始位置だけを記入することもできます。

```text
Preload Hint 可以提示 segment 23 中从 0 开始、长度为 4,044 字节的范围。
如果长度尚未确定，hint 只保留 byte-range 的起始位置。
```

キーポイント:

- トランスクリプトは、ヒントがセグメント 23 を指している可能性があることを明確に示しています`0`到着`4,044`範囲。
- バイト範囲の開始位置は、次の部分セグメントが親セグメントから始まる場所をクライアントに伝えます。
- バイト範囲の長さは、現在既知の範囲サイズをクライアントに伝えます。
- パッケージャがヒントを発行するときに長さが不明な場合は、長さを省略できます。

### CMAF チャンクとチャンク転送を使用した継続的配信

([04:17](https://developer.apple.com/videos/play/wwdc2020/10229/?time=257)) CMAF チャンクは、低遅延 HLS の部分セグメントにマッピングできます。サーバーは、複数のチャンクを同じ親セグメントに徐々に追加します。クライアントは親セグメントへのオープン要求を開始し、チャンク転送エンコーディングを通じて後続の部分セグメントを継続的に受信します。

```text
第一个更新：segment 1 的第一个 Partial Segment 是前 3,000 字节，hint 更新为从 3,000 开始。
第二个更新：segment 1 出现第二个 byte-range，hint 更新为从 8,000 开始。
```

キーポイント:

- トランスクリプトには、最初の部分セグメントがセグメント 1 の前であることが明確に記載されています`3,000`バイト。
- 次回のプレイリスト更新後、ヒントの開始位置は次のように更新されます。`3,000`。
- 次回の更新後、2 番目のパートが表示され、ヒントは次のパートの開始位置を示します。`8,000`。
- セッションでは、多くの CDN がライブ コンテンツのチャンク転送エンコーディングをサポートしていないことを思い出させます。このモデルを採用する前に、CDN 機能を検証する必要があります。

### サーバーに計画の変更を許可する

([07:42](https://developer.apple.com/videos/play/wwdc2020/10229/?time=462)) プリロードヒントは計画であり、約束ではありません。サーバーがヒントを解放した後も、次のコンテンツは変更できます。一般的なシナリオは、オペレーターが事前に広告からライブ ブロードキャストに戻ることを決定することです。

```text
服务器已经发布一个 hint。
运营方决定提前从广告返回直播。
下一次 playlist 更新没有包含之前 hinted URL。
客户端取消挂起的 hint 请求，改用 playlist 中真实出现的内容。
```

キーポイント:

- トランスクリプト サーバーはプリロード ヒントを発行した後も計画を変更できることを説明します。
- 一般的な理由は、運営者が早期に広告からライブ ストリーミングに戻ることを決定したことです。
- 次回プレイリストが更新されるときに、以前にヒントされた URL がプレイリストに表示されない場合、クライアントは保留中のリクエストをキャンセルします。
- その後、クライアントは実際にプレイリストに表示される新しい部分セグメントをロードします。

## 重要なポイント

- **低遅延ライブ ブロードキャスト用のリクエスト タイミング ダッシュボード**: ブロッキング プレイリストのリロード、プリロード ヒントのリクエスト、および部分セグメントのリターン時間を同じタイムライン上に描画します。実行する価値がある理由: Session は、これら 2 つのブロッキング リクエストが通常同時にハングし、ほぼ同時に返されることを強調しています。開始方法: プレイリスト リクエスト、ヒント リクエスト、HTTP ブロック解除時間、および一部の URI をプレーヤーとエッジ サービスのログに記録し、[OK] を押します。`#EXT-X-PRELOAD-HINT`位置合わせ。

- **HLS パッケージャーのヒントの整合性チェックを行う**: ヒント付きの各 URL が後続のプレイリストでヒントとして使用されるかどうかを確認します。`#EXT-X-PART`または`#EXT-X-MAP`現れる。実行する価値がある理由: サーバーは計画を変更できますが、一般的なエラーによりクライアントが無効なリソースを要求する可能性があります。開始方法: 連続したプレイリストのスナップショットを解析し、トレースする`#EXT-X-PRELOAD-HINT`、次の更新で URI とバイト範囲が一致することを確認します。

- **CDN 機能検出ツール**: ターゲット CDN がライブ ブロードキャスト シナリオのチャンク転送エンコーディングをサポートしているかどうかを確認します。実行する価値がある理由: CMAF チャンク ソリューションは、同じメディア サービスのセットである低遅延 HLS および低遅延 DASH を再利用できますが、セッションは、多くの CDN がこのライブ配信方法をサポートしていないことを明確に思い出させます。開始方法: テスト親セグメントへの長い接続リクエストを開始し、サーバーがチャンクを徐々に追加し、クライアントがデータをバッチで受信できるかどうかを記録します。

- **広告境界プリロード検証**: 特殊なテスト`TYPE=MAP`そして`TYPE=PART`広告挿入中の動作とライブブロードキャストへの早期のカットバック。実行する価値がある理由: セッションでは、MAP ヒントがコンテンツの切り替えに役立つと述べており、また、サーバーがアドバタイズ中に計画を変更する可能性があることも示しています。開始方法: ライブ ストリーミング、広告、早期リターンの 3 種類のプレイリスト更新を含むテスト ストリームを準備し、プレーヤーが古いヒントをキャンセルして新しいシャードをロードするかどうかを確認します。
