## Highlight

> Xcode 12 和 Instruments 把 Apple GPU 的 performance limiters、memory bandwidth、occupancy、HSR 等 counters 暴露到 encoder 和 draw call 级别，让 Metal 开发者能从最长的 pass 追到具体资源与 shader。

---

## 核心内容

一个 Metal 游戏掉帧时，最难的部分通常不是发现“GPU 很忙”。真正的问题是：哪个 render pass 拖慢了帧？是 ALU 在算太多，Texture Unit 在取太多数据，还是 Pixel Backend 写回太重？没有硬件计数器，开发者只能靠删效果、改 shader、反复试运行来猜。

这场 session 给出的做法更直接。先在 Instruments 的 Metal System Trace 里录制一帧，打开 Performance Limiters，找到最长的 command encoder。再进入 Xcode 的 Metal Debugger，把 counters 切到 encoder 或 per-draw 视角，按 ALU、Texture、Memory 等分组过滤，定位真正的硬件瓶颈。

Apple 还把这些数字放回 TBDR（Tile Based Deferred Renderer，基于 tile 的延迟渲染）架构里解释。Apple GPU 没有独立显存，CPU 和 GPU 共享 System Memory，rendering 阶段依赖片上的 Tile Memory。带宽、load/store、texture format、storage mode、draw order，都会直接影响一个 pass 是否高效。

## 详细内容

### 从 performance limiters 开始

（[05:58](https://developer.apple.com/videos/play/wwdc2020/10603/?time=358)）演讲者建议先看 Performance Limiters。GPU 会并行执行 arithmetic、memory access、rasterization 等任务，limiter counters 的作用是指出最慢的那个子系统。

```text
Profile order
1. Record with Instruments Game Performance template.
2. Enable GPU Counter Set: Performance Limiters.
3. Find the longest command encoder in the GPU timeline.
4. Compare top limiter: ALU, Texture Sampler, Texture Write, Buffer, Tile Memory, GPU LLC, Fragment Input Interpolation.
5. Open the same frame in Xcode Metal Debugger for encoder and draw-call counters.
```

关键点：

- 第 1 步先录真实设备上的 workload，因为 session 演示的是 iPad Pro 上的 Respawnables Heroes。
- 第 2 步打开 Performance Limiters，Instruments 会展示 top limiter 和各个 limiter track。
- 第 3 步避免平均值误导，先抓最长的 encoder，例如 demo 里的 Deferred Phase Encoder。
- 第 4 步把“慢”拆成具体硬件单元，后续优化才有方向。
- 第 5 步用 Xcode 做深挖，session 明确提到 Xcode 可以在 encoder 粒度列出全部 counters，并提供 draw call 子集。

### ALU limiter：先看精度和分支

（[10:22](https://developer.apple.com/videos/play/wwdc2020/10603/?time=622)）ALU（Arithmetic Logic Unit，算术逻辑单元）处理浮点、整数、位运算和关系运算。session 给出的第一条规则很简单：能用 16-bit floating point，就不要默认使用 32-bit floating point。

```text
ALU investigation workflow
1. Filter Xcode counters by ALU.
2. Compare floating-point 16 utilization with floating-point 32 utilization.
3. Inspect shaders in the longest encoder for complex operations such as square root.
4. Check whether branch conditions diverge inside a SIMD lane.
5. Verify that Metal shaders are compiled with the -ffast-math flag when the project can use it.
```

关键点：

- 第 1 步来自 session 的 Xcode filtering 建议，用 ALU 过滤器找 arithmetic-related counters。
- 第 2 步对应 demo 中发现 FP32 utilization 高于 FP16 utilization 的排查方式。
- 第 3 步来自 session 对 complex operations 的提醒，square root 这类操作可能低于示意图中的 best case rate。
- 第 4 步对应 coherent execution 与 divergent execution 的对比：同一个 SIMD lane 共享 program counter。
- 第 5 步来自 session 的优化清单，`-ffast-math` 是演讲中明确点名的 Metal 编译选项。

### Texture 和 bandwidth：从格式、压缩、storage mode 查起

（[14:40](https://developer.apple.com/videos/play/wwdc2020/10603/?time=880)）Texture Sample limiter 高时，session 重点提醒了三个方向：mipmaps、filtering options、texture compression。RGBA32Float 这类 128-bit format 会以 quarter rate sample，高精度纹理如果只是噪声图或 lookup table，代价可能过高。

```text
Texture and bandwidth investigation workflow
1. Filter Xcode counters by Texture and Memory.
2. Sort the table by bytes read from main memory.
3. Switch from encoder counters to per-draw counters.
4. Inspect the bound resources for the draw with the most texture L1 bytes transferred.
5. Check pixel format, mipmap usage, filtering, compression, and storage mode.
```

关键点：

- 第 1 步和第 2 步来自 demo：先切到 Memory group，再按 Bytes Read From Main Memory 排序。
- 第 3 步来自 Xcode 的 Per-Draw Counters mode，用它把 encoder 问题缩小到具体 draw call。
- 第 4 步对应 Bound Resources 视图，demo 在这里发现 RGBA16 floating-point cube map texture。
- 第 5 步只列 session 明确讨论过的检查项：pixel size、mipmaps、filtering options、block compression、lossless compression、storage mode。
- demo 的具体优化是把 sampled texture 从 shared storage 改为 private storage，让 lossless texture compression 降低 bandwidth。

### Tile Memory、Buffer、GPU LLC：把数据留在合适的位置

（[17:34](https://developer.apple.com/videos/play/wwdc2020/10603/?time=1054)）Tile Memory limiter 关联 Imageblock 和 Threadgroup Memory。它会出现在 tile shader、programmable blending、compute shader threadgroup memory 等场景。session 给出的检查点是 atomics、parallel reductions、SIMD lane operations、16-byte alignment 和 memory access pattern。

```text
Tile Memory investigation workflow
1. Filter Xcode counters by Imageblock or Threadgroup Memory.
2. Identify compute shaders that use threadgroup memory.
3. Reduce threadgroup atomics when they dominate the limiter.
4. Prefer threadgroup parallel reductions or SIMD lane operations where the algorithm allows it.
5. Align threadgroup memory allocations and accesses to 16 bytes.
6. Reorder memory access patterns for higher efficiency.
```

关键点：

- 第 1 步来自 session 的命名说明：工具和文档中会把 Tile Memory 显示为 Imageblock 和 Threadgroup Memory。
- 第 2 步对应 session 中的 compute dispatches 与 threadgroup memory 场景。
- 第 3、4 步来自演讲给出的 atomics 优化建议。
- 第 5 步保留了 session 明确给出的 16-byte alignment 要求。
- 第 6 步对应演讲中 reordering memory access patterns 的建议。

（[18:52](https://developer.apple.com/videos/play/wwdc2020/10603/?time=1132)）Buffer Read/Write limiter 高时，要检查 device 与 constant address space。大量 fragment 或 vertex 按索引读取的数据适合 device；许多线程共享的只读数据适合 constant。

```text
Buffer limiter investigation workflow
1. Filter Xcode counters by Buffer.
2. Separate read-only data used by many vertices or fragments from indexed per-vertex or per-fragment data.
3. Use constant address space for broadly reused read-only data.
4. Use device address space for data indexed per fragment or per vertex.
5. If the limiter stays high, inspect packing, smaller types, vectorized load/store, device atomics, and register spills.
```

关键点：

- 第 1 步来自 session 的 Xcode filtering 建议，输入 Buffer 可以看到 Buffer Read、Buffer Write 和 limiter。
- 第 2 步是 transcript 中对 buffer data address spaces 的分类。
- 第 3 步对应 constant address space：适合 many vertices or fragments 共同使用的 read-only data。
- 第 4 步对应 device address space：适合 per-fragment 或 per-vertex indexed data。
- 第 5 步保留了 session 的优化清单：pack data tightly、smaller types、vectorize load/store、avoid device atomics 和 register spills。

### Occupancy 和 HSR：计数器要一起读

（[23:24](https://developer.apple.com/videos/play/wwdc2020/10603/?time=1404)）Occupancy 衡量 GPU 使用了多少线程容量。session 特别提醒，高 occupancy 或低 occupancy 本身都不等于问题。低 vertex occupancy 可能没关系，只要 fragment occupancy 足够；低 overall occupancy 可能说明 shader 耗尽了 tile/threadgroup memory，也可能只是渲染区域太小。

```text
Occupancy checklist
- Query maximum threads per threadgroup.
- Query SIMD execution width.
- Query static threadgroup memory length.
- Correlate occupancy with ALU, texture, buffer, and bandwidth counters.
```

关键点：

- `maximum threads per threadgroup`、`SIMD execution width`、`static threadgroup memory length` 都来自 session 中列出的 pipeline static properties。
- occupancy 只能和其他 counters 联读，不能单独作为优化目标。
- 如果线程池没跑满，要继续查内部资源、command size、render area、compute grid size。

（[25:54](https://developer.apple.com/videos/play/wwdc2020/10603/?time=1554)）HSR（Hidden Surface Removal，隐藏面移除）用于减少 overdraw。session 给出一个可测量定义：overdraw 是 Fragment Shader invocations 和 Pixels Stored 的比值。

```text
HSR optimization order
1. Draw opaque meshes first.
2. Then draw alpha test, discard, and depth feedback.
3. Draw translucent meshes last.
4. Avoid interleaving opaque and non-opaque meshes.
5. Avoid interleaving opaque meshes with different color attachment write masks.
```

关键点：

- 第 1 步让 HSR 尽早建立 front-most visible layer。
- 第 2 步把会影响可见性的特殊材质放在 opaque 之后处理。
- 第 3 步符合 translucent meshes 依赖 blending 的现实限制。
- 第 4、5 步来自 session 的明确建议，目标是让 HSR 保持高效率。

## 核心启发

- **做什么**：给游戏内置一个“性能场景”菜单，自动跳转到战斗、主城、后处理压力测试等固定场景。
  - **为什么值得做**：session 的工作流从真实 frame 出发，固定场景能让 Instruments 和 Xcode 捕获可比较的 counters。
  - **怎么开始**：为每个场景加调试入口，录制 Metal System Trace，先比较 top performance limiter 和最长 encoder。

- **做什么**：为材质系统增加“纹理带宽审计”报表。
  - **为什么值得做**：session demo 通过 per-draw counters 找到 shared RGBA16 floating-point cube map，并建议改成 private storage 或 block compression。
  - **怎么开始**：扫描纹理的 pixel format、mipmap、storageMode、compression 状态，把 RGBA32Float、无 mipmap、shared sampled texture 标为高优先级检查项。

- **做什么**：在 shader review 中加入 half precision 和 divergent branch 检查。
  - **为什么值得做**：session 明确说明 F16 是 double rate，divergent execution 会让同一个 SIMD lane 付出额外 cycles。
  - **怎么开始**：从 ALU limiter 最高的 encoder 开始，审查 fragment shader 中的 FP32 输入、复杂函数、隐式转换和数据相关分支。

- **做什么**：为透明物体、alpha test、opaque mesh 建立稳定的 draw order 策略。
  - **为什么值得做**：HSR counters 可以衡量 overdraw；session 建议先 opaque，再 alpha/discard/depth feedback，最后 translucent。
  - **怎么开始**：在 renderer 的 render queue 中按 visibility state 分桶，再用 Fragment Shader invocations 与 Pixels Stored 的比值验证改动。
